## 1. 背景と問題意識

PoC では「話す → 整理 → プラン生成」の一気通貫が疎通済み（`basic_design.md`）。
しかし `concept_deck.md` §1 の核心課題 —— **「同じ悩みを何度も話している / 継続テーマが見えない」** —— を**まだ解けていない**。

理由は設計の構造にある:

- 集約ルートが **会話セッション**になっている（`HistoryItem` も 1 セッション = 1 レコード）
- 困りごとは `OrganizedResult.priorities: string[]` という、**要約に畳まれたただの文字列配列**でしか表現されない
- 困りごとが **セッションを跨いで同一物として残らない**ため、蓄積・横断・再出現検知ができない

→ **v1 の狙い**: 困りごし（**Problem**）を第一級のドメイン対象に昇格させ、**セッションを跨いで蓄積・分解・ラベリング・横断閲覧**できるようにする。これが「会話で終わらず自己理解が資産として育つ」（concept_deck）を実際に成立させる最小の構造転換。

## 2. スコープ

### 2.1 v1 で扱う（in scope）

1. 音声 / テキストで「モヤモヤ」を吐き出す（既存 STT = Web Speech API を活用）
2. 吐き出しから **Problem を抽出・分解**する
3. Problem の **ラベリング / 分類**
4. Problem の **セッション跨ぎ蓄積・永続化**（in-memory からの脱却）
5. 溜まった Problem の **横断閲覧 / 一覧 / 検索**
6. Problem の **ライフサイクル管理**（open → … → 解決 / 棚卸し）
7. 既存の **アクションプラン生成**を Problem に接続

### 2.2 次フェーズ（out of scope。設計は別ラウンド）

- **定期的な自動整理**（スケジュールでの棚卸し / ダイジェスト生成）
- **AI による状況ウォッチ & プロアクティブなアナウンス / nudge**

> 切り出す理由: concept_deck §4「Plan 提案は毎回必須にしない / 望まれたときだけ次の一歩」という**プロアクティブ抑制の設計思想**と、「AI が能動的にアナウンスする」構想は思想レベルで対立する。ここは v1 の蓄積基盤が固まってから、**思想転換を ADR で明示判断した上で**設計する。v1 は「溜まる・見える」までを確実に作る。

### 2.3 当面触らない（concept_deck §13 の後回し方針を踏襲）

- 高度な統計ダッシュボード / 思考傾向分析
- Notion 等との本格外部連携・タスク自動同期
- 音声 UI の高度最適化

## 3. 用語（暫定 / 正式定義は `domain_model.md`）

| 用語 | 暫定の意味 |
| --- | --- |
| **Dump（吐き出し）** | ユーザーが音声 / テキストで一気に話した未整理の入力 |
| **Problem（困りごと）** | Dump から抽出される、**追跡可能な単位**の関心事 / 悩み。id・ラベル・状態・起源を持つ第一級エンティティ |
| **Session（セッション）** | 1 回の対話。複数の Dump を含み、0〜N 個の Problem を生む / 既存 Problem に再接続する |
| **Label（ラベル）** | Problem を分類・横断するためのタグ / カテゴリ |
| **再出現（recurrence）** | 過去の Problem と実質同一の関心事が別セッションで再び語られること |

---

## 4. アクター

| アクター | 種別 | v1 での役割 |
| --- | --- | --- |
| **ユーザー** | 主アクター（人間） | 内省したい知的労働者（concept_deck §8）。吐き出す / 抽出結果を確認・修正する / 溜まりを見返す。**ゴールの主体** |
| **LLM サービス（Azure OpenAI）** | 補助アクター（外部） | 抽出・ラベリング・整理・プラン生成をシステムから委譲される |
| **音声サービス（Web Speech / VOICEVOX）** | 補助アクター（外部） | STT（入力）・TTS（出力）を担う |

> **AI はアクターではなくシステムの責務**: 困りごとの抽出・ラベリング・整理・再出現検知は、外部から系に働きかける主体ではなく、システム自身の振る舞いとして設計する（実体は上記 LLM サービスへの委譲）。v1 ではこの振る舞いは**受動的**（ユーザー操作に応答）。
> 次フェーズの「AI が能動的にウォッチ・アナウンスする」構想は、*アクターが増える*のではなく*システムが能動化する*変更として扱う。

## 5. ユースケース一覧（index。詳細は `use_cases.md`）

すべて**ユーザーのゴール粒度**で揃える。AI による分解・ラベリング・再出現検知は、各 UC 内の*システムの振る舞い*として記述する。

| ID | 名前 | 概要 |
| --- | --- | --- |
| UC-01 | モヤモヤを吐き出して困りごとに整理する | 音声 / テキストで一気に吐き出し、システムが Problem 群に分解・提示、ユーザーが承認 / 統合 / 分割 / 却下する（human-in-the-loop） |
| UC-02 | 溜まった困りごとを見返す | 蓄積された Problem をラベル / 時系列 / 状態で一覧・検索する |

## 6. 機能要件（FR）

> 各要件は「無いと何が静かに壊れるか」を 1 文で言えること（`docs/testing/strategy.md` の方針に揃える）。受け入れ基準は後続でテスト化する前提で書く。

- **FR-1 吐き出し入力**: ユーザーは音声（既存 STT）またはテキストで Dump を入力できる。
  - 受け入れ: 音声入力が利用不可な環境でもテキストで完結できる。
- **FR-2 Problem 抽出**: システムは 1 つの Dump / セッションから 0〜N 個の Problem を抽出・分解できる。
  - 受け入れ: 1 回の吐き出しに複数の悩みが含まれる場合、それぞれ別 Problem になり得る。
  - **未決**: 抽出のタイミング（発話ごと同期 / セッション終了時バッチ）→ §9。
- **FR-3 ラベリング**: 抽出された各 Problem に、分類用のラベルが付与される。
  - **未決**: 固定 taxonomy か自由生成か → §9。
- **FR-4 蓄積・永続化**: Problem はセッション終了後も永続化され、再起動 / 再ログインで消えない。
  - 受け入れ: PoC の in-memory（再起動で消える）を脱却している。
- **FR-5 横断閲覧**: ユーザーは蓄積された Problem をラベル / 状態 / 時系列で一覧・絞り込みできる。
  - 受け入れ: 「この 1 ヶ月で繰り返し出ているテーマ」が画面上で識別できる。
- **FR-6 ライフサイクル**: 各 Problem は状態を持ち、ユーザー操作で遷移できる（最低限: open → 解決 / 棚卸し）。
  - 受け入れ: 解決済みは既定の一覧から外れるが、後から参照できる。
- **FR-7 再出現検知**: 新規 Dump が過去 Problem と実質同一のとき、システムは既存 Problem への接続を提案できる。
  - 受け入れ: 「同じ悩みを何度も話している」がユーザーに可視化される（concept_deck §1 の直接解決）。
  - **未決**: 同一性判定の手段（embedding 類似 / ラベル一致 / 人手確認）→ §9。
- **FR-8 ユーザーによる修正（human-in-the-loop）**: AI の抽出・ラベリング・接続提案は、ユーザーが承認 / 修正 / 却下できる。
  - 受け入れ: AI が勝手に確定せず、ユーザーが最終編集者（concept_deck「共同編集」）。
- **FR-9 プラン接続**: ユーザーは 1 つ以上の Problem を選んでアクションプランを生成できる（既存 `consultation.createPlan` を再接続）。

## 7. 非機能要件（NFR）

- **NFR-1 プライバシー / データ保護（最重要）**: メンタル状態に関する機微情報を扱う。保存データの暗号化、ユーザーによる削除権、保管リージョンの明確化を前提とする。
  - 注: 医療的な診断・治療ではなく自己理解支援というプロダクト位置づけ（concept_deck 冒頭注）を UI / 文言レベルでも保つ。
- **NFR-2 永続化の信頼性**: Problem / 履歴は耐久性のあるストアに保存（basic_design §10 の Cosmos DB / Redis 方針と接続）。
- **NFR-3 音声対話のレイテンシ**: 「心理的に疲れにくい」体験（concept_deck §7）のため、吐き出し → 受け止め応答、および抽出結果提示までの体感速度を許容範囲に保つ。
  - **未決**: 抽出を同期にするとレイテンシが増える（basic_design の 2 段呼び出し懸念と同種）→ §9。
- **NFR-4 コスト**: Container Apps の scale-to-zero 方針を維持（ADR 0002）。
- **NFR-5 観測性**: 抽出精度・再出現検知の妥当性を後から評価できるよう、最低限のログ / 指標を残す。

| 影響 | 内容 | 対応 |

## 9. オープンクエスチョン（決めないと先に進めない論点）

1. **抽出タイミング**: 発話ごとに同期抽出か、セッション終了時にまとめてバッチ抽出か（UX とレイテンシのトレードオフ / NFR-3）。
2. **Problem の粒度**: どこまで細かく割るか。「転職を考えている」は 1 つか、複数の小問に割るか。粒度の指針が要る。
3. **同一性 / 再出現判定**: 過去 Problem との「実質同一」をどう判定するか（embedding 類似 / ラベル / 人手）。FR-7 の実現方式。
4. **ラベル体系**: 固定 taxonomy（一覧の比較性が高い）か、LLM 自由生成（表現力が高いが揺れる）か、両者併用か。
5. **音声の主役度**: v1 で音声をどこまで主軸にするか（PoC は Web Speech API。サーバ STT は未導入）。
6. **編集の最終権**: AI 抽出をユーザーがどこまで・どの操作粒度で直せると十分か（FR-8 の具体）。
