## 1. TTS 文分割 (`domain/sentences.ts` — `splitTtsSentences`)

読み上げテキストを合成単位の「文」に分割する。分割アルゴリズムを BFF だけが持つ理由 (キャッシュキー一致) は実装コメントと ADR 0024 の文脈を参照。

**現行仕様**:

1. 区切り文字は `。 ． ！ ？ ! ? 改行` 。**連続する区切り文字はひとまとめ**に扱う (「えっ！？」で 2 分割しない)
2. 区切り文字は**直前の文側に残す** (分割は文字を消費しない)
3. **空白のみの断片は捨てる** (例: 区切り文字の後に空白だけが続く場合)
4. **8 文字未満の断片は隣の文に併合する** (「はい。」の単独合成による不自然さ・合成往復の増加を防ぐ)。前方の文への併合が基本で、末尾の短断片も直前の文へ併合する

**性質 (プロパティテストが固定しているもの / `domain/sentences.property.test.ts`)**:

- **内容保存**: 分割して連結すると、**空白のみ断片の除去を除いて**元の文字列に戻る。空白を含まない入力では厳密な往復が成り立つ。全入力で成り立つのは「空白を除いた内容と並びの保存」
  - NOTE: テスト戦略の性質候補は「分割して連結すると元の文字列に戻る」だったが、上記 3 (空白のみ断片の除去) があるため厳密には成り立たない。**プロパティテストを書いたことで判明した仕様の穴** (2026-08-11)。挙動としては読み上げに影響しないため現行仕様として明文化した
- 出力に空白のみの文は含まれない
- 2 文以上に分かれたら、どの文も 8 文字以上
- 空配列になるのは空白のみの入力に限る

**未決**: なし (空白のみ断片の除去は読み上げ結果に影響しないため、現行仕様として確定扱いでよいと判断。異論があれば debrief で)。

## 2. セッションタイトル導出 (`domain/title.ts` — `deriveTitle` / frontend `sessionTitle.ts` — `deriveSessionTitle`)

相談セッションの見出しを発話テキストから導出する。BFF (実 API の `consultation.start`) とフロント (mock の自動リネーム) の 2 実装があり、**切り詰め長 26 は両者で揃える** (mock と実 API で見出しの長さが変わる非対称を防ぐ。2026-08 に実際に 18/26 の食い違いが見つかり PO 判断で 26 に統一した経緯がある)。

**現行仕様**:

1. 前後の空白を除去する。空になったら既定タイトル (BFF: 「相談セッション」 / frontend mock: 「新しい相談」 — 用途が違うため文言差は意図)
2. **26 文字を超えたら 26 文字で切り詰めて省略記号「…」を付ける**。したがって**最大長は 27 文字** (本文 26 + 省略記号 1)
   - NOTE: テスト戦略の性質候補は「常に 26 文字以下」だったが、省略記号を数えると 27。**プロパティテストを書いたことで判明したズレ** (2026-08-11)。「本文 26 + 省略記号」を現行仕様として確定
3. frontend 版のみ、改行・連続空白を 1 つの空白に畳む (見出しを必ず 1 行にする)。BFF 版は畳まない

**性質 (プロパティテストが固定しているもの)**: 空にならない / 長さ ≤ 27 / 26 文字以下の入力は不変 / (frontend) 1 行に畳まれる。

**未決**:

- **サロゲートペア切断**: 切り詰めが UTF-16 コードユニット単位 (`String.prototype.slice`) のため、26 ユニット目が絵文字などサロゲートペアの途中に落ちると**文字が壊れて「�」が表示される**。また絵文字は 1 文字で 2 ユニット消費するため「26 文字」も表示文字数と一致しない。`domain/title.property.test.ts` の `it.fails` が現状を固定している。修正するならコードポイント (`[...str]`) か書記素単位の切り詰めに統一する (BFF / frontend 両方)
- **空白畳み込みの非対称** (上記 3): 改行入りの concern を BFF に渡すと複数行のタイトルが返る。frontend に揃えるか、現状維持か

## 3. Problem の派生フィールド (`domain/problem.ts`)

構造とライフサイクルの真実は [`domain_model.md`](./domain_model.md) §2.2 (mentionCount = mentions の派生) / §4.2 (再燃は自動) / §6 (不変条件)。ここには導出の**詳細**だけを書く。

**現行仕様**:

1. **`mentionCount` は常に `mentions.length` から導出する**。ai-agent の申告値 (`grouping.mentionCount`) は使わない (候補集合のズレ・再送で実体と食い違うため)。追記 (`appendMention`) / 新規 (`problemFromMention`) / 統合 (`mergeProblems`) / 再リンク (`withDerived`) のすべての経路で成り立つ
2. **再言及の追記は必ず `open` に戻す** (再燃自動 / domain_model §4.2)。棚卸し日時 (`resolvedAt` / `shelvedAt`) も消す
3. 統合は Mention を取りこぼさず移し (`problemId` を統合先に付け替え)、tags は重複除去した和集合、plans は連結
4. `lastMentionedAt` の導出は**経路によって違う**:
   - `appendMention` (抽出の追記): **追記した Mention の `createdAt` を無条件採用**
   - `withDerived` (relink / merge): **mentions の最大 `createdAt` を再計算**

**未決**:

- **`lastMentionedAt` の導出不一致** (上記 4): 過去日時の Mention が後から追記される (再送・バックフィル・時計ずれ) と、追記経路では `lastMentionedAt` が**逆行**し、休眠判定 (domain_model §4.2 の派生ビュー) や並び順が狂いうる。`domain/problem.property.test.ts` の `it.fails` が現状を固定している。「常に max」へ統一するのが素直だが、domain_model の「最終言及」の定義 (語られた日時の最大か、最後に追記された事実か) の裁定が必要
