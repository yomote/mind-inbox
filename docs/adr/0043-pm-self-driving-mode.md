# 0043. PM を自走モードにする — 実物指標・週次目標・引く当番・日次ダイジェスト・窓口台帳

- Status: Proposed
- Date: 2026-08-11
- Deciders: yomote (PO — 方向は 2026-08-11 の対話で合意。Accept は次回 debrief) / PM セッション
- Related: [ADR 0040](0040-project-continuity-three-layers.md) (継続性 3 層 — 本 ADR は D2/D3 の拡張) / [ADR 0021](0021-parent-session-as-pm-orchestrator.md) (hub-and-spoke — 条項の機構化) / [ADR 0033](0033-parent-implements-via-subagent-when-child-sessions-are-gated.md) (分配基準) / [ADR 0036](0036-merge-gate-as-required-check-and-pm-cadence.md) (マージの門と PM リズム) / [ADR 0014](0014-design-comprehension-gate-and-debrief.md) (理解ゲート — 規律は不変)

Technical Story: 当番 Routine (ADR 0040 D2) 初発火後の 2026-08-11 PO レビュー対話。宿題二重起票 [#270](https://github.com/yomote/mind-inbox/issues/270) / status ページ「プロダクトの現在地」PR #281。

## Context and Problem Statement

当番 Routine ([ADR 0040](0040-project-continuity-three-layers.md) D2) の初発火で「巡回だけでなく執行までやる」ことは実証された。しかし PO から構造的な問題が 3 点指摘された:

1. **PM が受け身** — 滞留の解消・レビュー対応は回るようになったが、報告会の開催すら PO が依頼している。「次に何をやるか」を提案し、進捗を PO の前に運ぶ側の駆動が無い
2. **進捗が見えない** — 「進んでるようで物ができてない」。実測: 2026-08-11 のマージ 14 本のうちプロダクト (apps/ を触るもの) は 3 本、しかも deploy 7 連敗 ([#262](https://github.com/yomote/mind-inbox/issues/262)) で dev には 1 本も届いていない。マージ数・Issue 処理数という工場の指標が、プロダクトが止まっている事実を覆い隠す
3. **集約点がセッションと共に揮発する** — 窓口 PM・当番 PM・並行セッションが増えた結果、窓口が 2 本並走し、同じ宿題が二重起票される ([#270](https://github.com/yomote/mind-inbox/issues/270) の実例)。ADR 0021 の「窓口は常に 1 本」は規律であり機構ではないため、セッションの揮発と蘇生 (コンテナ回収後の再開) に耐えられない

要するに、0040 で「止まらない」は作れたが、**「正しい方向に自分で進む」と「進んだかどうかが PO に見える」が無い**。PM を巡回員から運転手にする必要がある。

## Decision Drivers

- **PO の巡回・依頼をゼロに近づける** — PO は返信するだけ、見に行かない (ADR 0020 / 0033 の driver を継承)
- **プロダクトの前進とメタ作業 (工場整備) を混同しない** — 指標が嘘をつかないこと
- **セッションの揮発に耐える** — 集約点・引き継ぎ・優先順位が GitHub に残ること (ADR 0011 / 0040 と同じ原則)
- **PO の関与が減っても暴走しないこと** — design-gate (ADR 0014) と WIP 上限 (ADR 0036 D5) の規律は崩さない
- **追加課金ゼロ・長期クレデンシャル増加ゼロ** (ADR 0008 / 0031 / 0037 の driver を継承)

## Considered Options

- Option A: 現状維持 — ADR 0040 の 3 層のみ (当番は巡回・執行、駆動と優先判断は PO 起点)
- Option B: Actions 経由の Claude 常駐 — 判断ごと GitHub Actions に置いて完全無人化
- Option C: **PM 自走モード** — 実物指標 + 週次目標 + 引く当番 + 日次ダイジェスト + 窓口台帳 (採用)

## Decision Outcome

Chosen option: **"Option C"**。LLM を無人経路に増やさず (B の却下理由は下記)、0040 の枠組みの上に「方向 (D2)・駆動 (D3)・可視化 (D1/D4)・集約 (D5)」を足す。

### D1 — 報告の一級指標は「実環境で触れるようになったもの」

- 日次ダイジェスト (D4) と status ページ冒頭 (PR #281 の「プロダクトの現在地」) は、**dev で実際に触れるようになった変化**を先頭に置く
- **ゼロの日は「ゼロ。理由は X」と書く** — deploy 赤で届いていない、マージが全部工場整備だった、等。ゼロを空欄や省略で隠さない (「静かに嘘をつかない」— ADR 0037 の driver と同じ)
- マージ数・Issue 処理数は脚注に落とす。工場の稼働量はプロダクトの前進ではない (2026-08-11 の実測: マージ 14 本 / プロダクト 3 本 / dev 到達 0 本)

### D2 — 週次プロダクト目標で運転する

- **「金曜に dev で触って確かめられるもの」を 1 つ**、PM が提案し PO が決める (初回: 2 ペイン化 [#187](https://github.com/yomote/mind-inbox/issues/187) — 2026-08-11 PO 決定)
- GitHub milestone で表現する。当番も窓口も、仕事を引くときはこの目標に向けて引く
- **メタ作業 (工場整備) は「プロダクトを止めている時だけ」着工可**。それ以外は Issue 化のみして目標優先に戻る。ADR 0040 D2 の当番職務「実務を回す」に方向を与える拡張

### D3 — 当番に「引く権限」と WIP 上限

- in-flight が空いたら、当番は**優先順位リストから次を自分で着工してよい** (0040 D2 の当番は「滞留の解消」まで — 本項が「次の仕事を引く」を追加する)
- 優先順位リストは PM 案を PO が整理したもの。並べ替えの指示はダイジェストへの返信 or 対象 Issue へのコメントで出す
- **WIP 上限: 2 (担当主体を問わない全実装ストリームの総数)** — 「着工中 + レビュー対応中の PR」を**誰が回しているかにかかわらず**数え、2 に達していたら新規着工しない。ADR 0036 D5 の実装ストリーム上限 2 本をそのまま総上限として使う (当番の分だけ数えると、他セッションが 1 本回している状態で当番が 2 本開始でき、実 WIP が 3 本になって 0036 の上限を超える)。**裁定待ち・PO 保留で止まっている PR は数えない** — 上限の目的は「同時に動く実装の衝突とレビュー滞留を防ぐ」ことで、止まっているものは衝突しないため
- **保留解除も「枠を取る」操作として扱う** — 除外があるので、保留 2 本を外に置いて別の 2 本を回している状態で PO が保留を解除すると、再開は「新規着工」ではないため上限に引っかからず実 WIP が 3 本になる。したがって**再開時にも空き枠を確認する**。埋まっていたら、**解除された PR を優先し、当番が回している方のうち後から着工した 1 本を止める** (レビュー待ちの状態で置き、新しい push をしない) — PO が保留を解いたということはそれが優先だから。止めた側は次の tick で枠が空き次第再開し、**どちらを止めたかをダイジェストに 1 行書く** (黙って止めない)
- **design-gate 級は着工せず裁定キューへ** — ADR 0014 の規律は不変。無人セッションがゲートを通せないことも不変
- **「閉じる」も当番の職務に含める** — 重複検出・完了済み close のトリアージ。開く自動化 (自動起票) と閉じる自動化を対にする (2026-08-11 に open Issue 48→39 件の一括トリアージを人力で実施した経緯。開く側だけ自動化すると台帳は太り続ける)

### D4 — 問いは日次ダイジェスト 1 通に束ねる

- 当番の最終 tick (18:00) が 1 コメントに集約する: **「今日 dev で変わったこと (D1 の一級指標)」/「🙋 あなたの番 (全部選択肢形式 — ADR 0020)」/「明日の予定 (優先順位案)」**
- 日中に散発した needs-human 起票は、ダイジェストが拾い直して 1 通にまとめる。**PO は返信するだけで、見に行かない**
- **PO が返信しない日は「ゲート対象だけ止まり、他は全部進む」が仕様** — 無応答は障害ではなく通常運転。裁定待ちのものだけがキューに残る

### D5 — 窓口台帳: 集約点はセッションではなく GitHub

- 常設の **「PM ハブ Issue」を 1 本**立てる。対話セッションは PM として動き始める前に、**引き継ぎ宣言を 1 コメント投稿する** (セッション ID / 開始時刻)
- 各セッションは **wake のたびに台帳を確認**し、自分より新しい宣言があれば「in-flight を書き残して黙って退役」する — コンテナ回収から蘇生したゾンビ窓口が旧文脈のまま並走する事故 (窓口 2 本化の実例) を機構で防ぐ
- **起票・着工の前に台帳と直近 PR を確認する** — 二重起票 ([#270](https://github.com/yomote/mind-inbox/issues/270)) の防止。「GitHub のライブ状態が唯一の真実」(ADR 0011 / 0021 条項 3) の起票側への適用
- **着工そのものは claim ref の CAS で原子的に取る** — 着工の第一手として、**Issue ごとに完全に同一の ref `refs/heads/claim/<Issue 番号>`** へ、**セッション固有の空コミット** (本文にセッション ID と時刻) を push する。ref の更新は GitHub 側で atomic な compare-and-swap なので、先着だけが成功し、後発は非 fast-forward で拒否される。**push 成功だけを担当の証拠にしない** — push 後に ref を fetch し直し、**そこに載っているコミットが自分のものであることを確認**してから着工する (push が no-op で成功する経路を塞ぐ二段確認)。作業ブランチ名 (`claude/<Issue 番号>-<slug>`) は人間可読性のためであり、**排他の役割は持たない** (slug が違えば別 ref になるため)
- **claim には解放と失効を必ず付ける** — 付けないと、着工セッションがクラッシュ・退役した瞬間にその Issue が**恒久的に着工不能**になる (残った claim commit に対して後続の push が永久に非 fast-forward で弾かれる)。使い捨てローテーションを前提にする以上、これは例外ではなく通常運転:
  - **解放 (正常系)**: PR が merge / close されたら、着工者が `refs/heads/claim/<Issue 番号>` を削除する。取りこぼしは当番 tick が拾う (open PR も open Issue も無い claim ref を掃除する)
  - **失効 (異常系)**: claim commit の時刻から **6 時間**経ち、かつ対応する PR が無い (または PR も作業ブランチも同じだけ動いていない) claim は**死んでいるとみなす**。後継は claim ref を **`--force-with-lease=refs/heads/claim/<n>:<観測した旧 SHA>` で奪取**する — 旧 SHA を expect に置くので、同時に 2 セッションが奪いに来ても成功するのは 1 つだけ (CAS は維持される)。奪取後は push 後の再 fetch 確認 (上記の二段確認) を同じように行う
  - **奪取は沈黙で行わない** — 奪ったセッションは対象 Issue に 1 行残す (旧 claim の SHA / 経過時間 / 奪取した理由)。「なぜ担当が入れ替わったか」が GitHub 側だけを見て分かること (ADR 0011)

**台帳は排他ロックではない (この機構の限界)**: コメントの投稿と確認の間には競合窓が残るため、「A が宣言 → 確認 → B が宣言」の順で両者が自分を最新と判断する状態は原理的に作れる。台帳が消すのは**時間軸の離れた事故** (コンテナ回収から数時間後に蘇生したゾンビ窓口が旧文脈で並走する / 別セッションが昨日片付けた宿題を積み直す) であり、秒単位の同時起動ではない。後者に対する防御は 2 つ — (1) 「対話セッションを同時に開かない」という PO 側の運用前提 (ADR 0021 / CLAUDE.md)、(2) 上記の claim ref (CAS) による原子的な着工。**排他が必要なのは「同じ仕事を 2 回やる」ことであって「窓口が 2 つ存在する」ことではない**ため、着工側を原子的にすれば実害は塞がる、という設計判断

- 本項は ADR 0021 条項 6/7 (窓口 1 本・使い捨てローテーション) の**機構化**であり、CLAUDE.md の「対話セッションは既定で窓口 PM」(2026-08-11 PO 決定) を前提とする。規律 (タイトル規約・気をつける) から台帳 (書いて確認する) へ — 「規律は破られ、機構は守られる」(ADR 0036) の適用

### Positive Consequences

- PO の仕事が「見に行って発見する」から「1 日 1 通に返信する」に縮む。返信しなくてもゲート対象以外は進む
- 「進んでるようで物ができてない」が指標レベルで検出される — dev 到達ゼロの日は D1 がゼロと書くので、工場の稼働量で誤魔化せない
- 週次目標が当番の「次に引く仕事」を規定し、優先判断のブレが小さくなる。誤った判断も翌日のダイジェストで可視化され 1 日で補正できる
- 蘇生ゾンビ窓口の並走と、日をまたいだ二重起票が台帳確認で消える。**同じ仕事の二重着工は claim ref の CAS で機構的に決着する** (窓口の同時存在そのものは台帳では排他できない — D5 の限界の項)。セッションの揮発・蘇生が問題でなくなる (0040 の到達点をさらに一段固める)

### Negative Consequences

- **PO の理解がループから薄まるリスク** — PO の関与が「返信のみ」に縮むと、設計の文脈が PO に蓄積されない。対策: 隔週の debrief / 報告会 (ADR 0014) で文脈を回復する二層構成。日次は運転、隔週は理解、と役割を分ける
- **ダイジェスト不達リスク** — 当番の最終 tick が落ちるとその日の問いが届かない。緩和: 当番レポートの欠落自体が watchers.json の監視対象 (ADR 0040 D2 と同じ機構) であり、翌朝の tick が拾い直す
- **当番の優先判断は間違いうる** — 引く権限を与える以上、誤着工は起きる。緩和: WIP 上限で被害を絞り、ダイジェストが翌日可視化する。不可逆な判断は元々ゲート対象で着工できない
- 台帳の確認・宣言という手順が全セッションに 1 ステップ増える (コメント 1 本 + 読み 1 回。二重作業のコストより安いという判断)
- milestone・ハブ Issue という GitHub 上の常設物が増え、放置されると陳腐化する — 週次目標の張り替えを怠ると D2 が形骸化する (ダイジェストの「明日の予定」欄が空くので検出は可能)

## Pros and Cons of the Options

### Option A: 現状維持 (ADR 0040 のみ)

- Good, because 追加の機構ゼロ。0040 の実装 (D1 sweep / 当番 Routine) だけ完遂すればよい
- Bad, because 3 つの指摘 (受け身 / 進捗が見えない / 集約点の揮発) がどれも残る。0040 は「止まらない」の解であって「進む方向」と「見せ方」の解ではない
- Bad, because 窓口 2 本化・二重起票は既に実害が出ており、規律のままでは再発する

### Option B: Actions 経由の Claude 常駐

- Good, because セッションの揮発問題が原理的に消える (サーバー側常駐)
- Bad, because **却下済みの経路** — `ANTHROPIC_API_KEY` は従量課金 (ADR 0008 / 0033 Option D)、OAuth トークンを CI に置くのは長期クレデンシャルの保存 (ADR 0037 / 0031 が同じ構図で棄却)。本 ADR で判断を再度開かない
- Bad, because 対話的な軌道修正ができず、PO の理解の希薄化がさらに進む

### Option C: PM 自走モード (採用)

- Good, because 0040 の枠組み (Actions / 当番 / 窓口) をそのまま使い、足すのは指標・目標・権限・束ね方・台帳という**運転の中身**だけ。無人経路の LLM も新しいクレデンシャルも増えない
- Good, because 各要素が既に実物で試作されている — 実物指標は PR #281、束ねる先は当番レポート Issue、台帳は既定 PM 化 (CLAUDE.md 2026-08-11) の延長
- Bad, because 機構の実装 (ダイジェスト形式 / ハブ Issue / milestone 運用 / 当番プロンプト改訂) が必要で、それまでは規律運用になる
- Bad, because PO の理解の希薄化リスクを debrief 側の運用に負わせる (上記 Consequences)

## 関係 ADR への影響

- **[ADR 0040](0040-project-continuity-three-layers.md)**: supersede しない。D2 (当番の職務) と D3 の運用に「週次目標へ向けて引く / 閉じる / WIP 上限 / ダイジェスト集約」を**拡張として追加**する。3 層構造と責務分界は不変
- **[ADR 0021](0021-parent-session-as-pm-orchestrator.md)**: 条項 6/7 (窓口 1 本・使い捨てローテーション) を D5 の台帳で**機構化**する。supersede ではなく実現手段の具体化 (タイトル規約が推奨どまりになった 2026-08-11 の CLAUDE.md 改訂と整合)
- **[ADR 0033](0033-parent-implements-via-subagent-when-child-sessions-are-gated.md)**: 分配基準 (作業の大きさ) は不変。当番が D3 で引いた仕事にも同じ基準を適用する
- **[ADR 0036](0036-merge-gate-as-required-check-and-pm-cadence.md)**: マージの門は不変。D4 (PM の運転リズム) の日次 tick が当番 tick + ダイジェストに具体化され、D5 (WIP 上限 2) は本 ADR D3 が着工判断側から補強する
- **[ADR 0011](0011-github-projects-as-execution-dashboard.md)**: 実行状態の真実は GitHub のまま。**見せ方**を status ページ (「プロダクトの現在地」+ D1 の実物指標) に寄せる
- **[ADR 0014](0014-design-comprehension-gate-and-debrief.md)**: design-gate / debrief の規律は不変。D4 の「返信しない日はゲート対象だけ止まる」はゲートの尊重であり緩和ではない

## 動作検証 (この ADR が実装されたと言える条件)

1. 日次ダイジェストが当番の最終 tick で 1 コメントとして積まれ、先頭が「今日 dev で変わったこと」(ゼロの日は理由つき) になっている
2. 週次目標の milestone が存在し、当番が引いた Issue がそこへ向いている
3. in-flight が空いた当番が、PO の指示なしで優先順位リストから次を着工する (WIP 上限内)
4. PM ハブ Issue に引き継ぎ宣言が積まれ、古いセッションが蘇生しても並走せず退役する (実測)
5. 二重起票が「台帳 + 直近 PR の確認」で未然に止まった実例が残る
