# 0022. UX 品質は自律改善ループで維持する — 観測・評価・改善 (PR まで) を自動化し、人間は基準定義と例外裁定に徹する

- Status: Accepted (briefing #1, 2026-08-08)
- Date: 2026-08-08
- Deciders: omoteforlab (方向性は 2026-08-08 の PM セッションで選択済み — 「PR 作成まで自動 / 会話品質から」)
- Consulted: —
- Informed: —

Technical Story: PO の実使用フィードバック (2026-08-08) で対話体験の課題群 (#119 応答が浅い / #120 即時性 / #121 音声途切れ) が判明。同時に PO から「今のクオリティで毎回確認していたらきりがない。**自律的に直せる仕組みがないと使い物にならない**」との提起。#122 (体験品質がループに伝わらない) の解決方針でもある。

## Context and Problem Statement

体験品質 (会話の深さ・応答の速さ・入力のしやすさ) は、このプロダクトの価値の芯でありながら、既存の検証ループ (ADR 0018 = 機能の動作検証 / ADR 0019 = リリース判定) のどの網にもかかっていなかった。さらに、仮に網を張っても「検知 → PO が確認 → 指示 → 修正」のループでは **PO の確認が律速**になり、改善の反復回数が人間の可処分時間で頭打ちになる。

品質改善の反復から人間を外せる部分を外し、**人間にしかできない仕事 (何が良い体験かの定義、判定不能例の裁定) に PO の時間を集中させる**構造が必要。

## Decision Drivers

- **PO の確認を律速にしない** — 改善の反復は機械が無限に回せる形にする
- **judge の信頼性** — LLM 評価の甘さ・自己満足を構造で抑える
- **既存資産の再利用** — golden-path 監視 (L4) / rubric-as-truth + 独立 judge (ADR 0019) / Routine (ADR 0008) / hub-and-spoke (ADR 0021) を組み合わせ、新規基盤を作らない
- **可逆性** — 自動で動くのは可逆な変更 (プロンプト等) と提案 (PR) まで。不可逆はゲートへ (ADR 0014)
- **コスト** — 毎朝の実環境プローブ + judge 数回で数十円/日のオーダーに収める (予算アラート内)

## Considered Options

- Option A: **自律ループ (PR 作成まで自動)** — 観測 → 評価 → 改善案の試作と盲検 A/B → 勝者を PR 化、までを無人で回す。マージは人間
- Option B: **評価レポートまで** — 観測と採点だけ自動化し、改善は人間起点
- Option C: **マージ・デプロイまで自動** — 可逆変更 (プロンプト等) に限り、A/B で勝ったら自動マージ

## Decision Outcome

Chosen option: **"Option A" (PR 作成まで自動)**。PO が 2026-08-08 に選択。ループは 4 段:

1. **観測 (毎朝・自動)** — golden-path monitor を「体験プローブ」に拡張。実環境で本物の相談シナリオを N 往復対話し、全応答文・区間レイテンシを記録として保存する
2. **評価 (自動)** — UX judge (新品コンテキストの subagent + `.github/claude/ux-rubric.md`, rubric-as-truth) が記録を採点する。観点例: 深掘りの問いを返しているか / オウム返しで済ませていないか / 感情の受け止めがあるか / レイテンシ閾値。スコアは時系列で蓄積し、トレンドを可視化する
3. **改善 (自動)** — スコアが閾値割れ or 前回比劣化のとき、Routine が改善子セッションを起動。プロンプト/対話設計の改案を試作し、**同一シナリオセットを新旧両案で流して盲検 A/B 比較** (どちらの会話が良いかを judge に順序・ラベルを伏せて判定させる)。勝った案だけを PR にする。負けた案は Issue にレポートとして残す
4. **検証と裁定 (人間)** — PR のマージは人間。PO が定常的に見るのは (a) 週次スコアトレンド 1 枚、(b) judge が判定不能 (UNKNOWN) とした例、(c) rubric の改定。**「何が良い会話か」の定義 = rubric だけは自動化しない** — これが PO の専権であり継続的な仕事

**初期スコープ**: 会話品質 (#119) から回す。レイテンシ (#120) は観測 (計測 + 閾値 warn) のみ先行し、改善は自律ループの対象外 (コード変更が大きく可逆性が低いため通常の Issue 駆動で)。音声入力 (#121) は対象外 (ブラウザ API / 課金 STT の判断が絡むため)。

### Positive Consequences

- 品質改善の反復回数が PO の可処分時間から切り離される。PO の仕事は「全応答の確認」から「基準定義 + 例外裁定 + マージ判断」に圧縮される
- 「浅い応答」の再発が毎朝機械検知され、劣化がトレンドとして見える (#122 の解決)
- rubric が明文化されることで、「良い会話」の定義自体が PR でレビュー・改善できる対象になる (ADR 0019 と同型)

### Negative Consequences

- **judge の信頼性リスク** — 生成側と judge が同系モデルだと評価が甘くなり得る。緩和: 絶対評価でなく盲検 A/B 比較を主軸にする (相対判定は絶対採点より頑健)。それでも残るリスクは PO の抜き打ち監査 (生ログを定期的に直接読む) で受ける
- **rubric への過適合 (Goodhart)** — 指標を最適化して体験が良くならない改善が通り得る。緩和: rubric 改定権を PO に置き、抜き打ち監査で乖離を検出したら rubric を直す
- **PR 滞留** — マージが人間なので、改善 PR が溜まる可能性。運用で様子を見て、実績が付いたら Option C (可逆変更の自動マージ) を新 ADR で再検討する
- コスト増 (プローブ + judge + A/B)。数十円/日のオーダー見込みだが、実測して予算アラートで監視する

## Pros and Cons of the Options

### Option A: PR 作成まで自動 (採用)

- Good, because 反復の律速が人間から外れ、かつ最終防衛線 (マージ) は人間に残る — 既存規約 (🟢 でも merge は人間) と整合
- Good, because 負けた改案も Issue レポートとして残り、探索の記録が蓄積する
- Bad, because マージ待ちが溜まる可能性 (運用で検証)

### Option B: 評価レポートまで

- Good, because 最小工事で judge の信頼性を見極められる
- Bad, because 「検知 → 人間が確認して指示」の律速構造が残り、提起された問題を解いていない

### Option C: マージ・デプロイまで自動

- Good, because 完全に無人で品質が上がり続ける (理想形)
- Bad, because 盲検 A/B の判定品質が未実証の段階で防衛線を外すのは早い。実績が付いてから新 ADR で再検討
