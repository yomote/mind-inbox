# 0027. UX 自律改善ループ M2 — 採点の無人化を先行させ、A/B は実環境の外で回し、改変対象はパスで縛る

- Status: Accepted (design-gate #3, 2026-08-08)
- Date: 2026-08-08
- Deciders: omoteforlab
- Consulted: —
- Informed: —

Technical Story: [Issue #123](https://github.com/yomote/mind-inbox/issues/123) M2。[ADR 0022](0022-autonomous-ux-improvement-loop.md) が「M2 は着手前に詳細設計 (トリガー条件 / A/B の判定プロトコル / 改変対象の境界) を design-gate に掛ける」と定めていたため、その 3 点を決める。

## Context and Problem Statement

ADR 0022 は UX 品質の自律改善ループを 4 段 (観測 → 評価 → 改善 → 裁定) で定め、M0 (観測) と M1 (評価の道具立て) が着地した。M2 = 3 段目「改善」の実装に入る前に、設計を確定する必要がある。

設計にあたって現物を読んだところ、**ADR 0022 の前提が 2 つ、実装と食い違っていた**。

### 発見 1: 「評価 (自動)」は自動ではない

ADR 0022 の段 2 は「評価 (自動)」と書かれているが、実装された運用 (`docs/runbooks/ux-probe-judge.md` Steps 2-4) は人手である:

- 記録 JSON の取得は人が `gh run download` する
- judge (`ux-reviewer`) の起動は人が Claude セッションから行う
- 採点結果の蓄積は「**呼び出し元セッションが**」スコアボード Issue [#127](https://github.com/yomote/mind-inbox/issues/127) へ転記する

さらに #127 自体が未着手 (Open・採点コメント 0 件) であり、**M2 のトリガーである「スコアが閾値割れ or 前回比劣化」を読む先が存在しない**。この状態で M2 を作ると、毎朝人間が judge を手で回さないと改善ループが起動しない — 自動化の目的と逆のものになる。

### 発見 2: 改変対象が v2 移行の対象ファイルと同一

改善ループが書き換える対象は `apps/services/ai-agent/app/workflow.py` の `CHAT_SYSTEM_PROMPT` (11 行) である。しかし同ファイルは [ADR 0016](0016-ai-agent-orchestration-on-maf.md) の M1-3 で MAF Workflow へ丸ごと置換される予定で、ファイル冒頭にもその旨が明記されている。**毎朝の自動 PR と人手の移行作業が同じファイルで衝突する**。

### 発見 3: A/B の実行場所が実環境に向く (設計中に判明)

新プロンプトを採点するには新プロンプトが動いている必要がある。素直に組むと「実環境のプロンプトを一時差し替えて比較する」形になり、2 つの害が出る:

- A/B の最中にアプリを使った PO が実験台になる
- ai-agent に「プロンプトを外部から上書きする口」が生まれる。ai-agent は Azure OpenAI の資格情報を持つため、**守るべき資源への扉が 1 枚増える** ([ADR 0017](0017-container-apps-access-via-auth-gate.md) / #86 と同型の失敗)

## Decision Drivers

- **トリガーが読む先が実在すること** — 自動ループの起点が人手だと自動化が成立しない
- **改変の境界が仕組みで縛られていること** — 約束 (起票文の指示) だけに依存しない ([ADR 0021](0021-parent-session-as-pm-orchestrator.md) の境界宣言は必要だが十分ではない)
- **守るべき資源への到達経路を増やさない** — 課金 (Azure OpenAI) / リポジトリ write / 実環境
- **判定が揺らぎに耐えること** — LLM の応答揺らぎと改案の効果を区別できること
- **コストは通常日で数十円/日を維持** (ADR 0022 の制約)

## Decision Outcome

以下 4 点を決定する (いずれも design-gate #3 で PO が選択)。

### D1. M1.5 (採点の無人化 + 機械可読な蓄積) を M2 の前に独立ステップとして切る

毎朝の採点を Routine 化する ([ADR 0008](0008-pr-review-via-cloud-routine.md) の PR レビュー Routine と同型): golden-path-monitor の完了後、Routine が artifact を取得 → `ux-reviewer` を**新品コンテキストの subagent** として起動 ([ADR 0019](0019-independent-judge-agents-security-qa-release.md)) → `ux-judge-score` JSON ブロックを #127 へコメント投稿する。

- 採点の書式・蓄積先・トレンド抽出 (jq) は**すでに rubric と runbook で定義済み**なので、新規に決めるものはない。人手の 3 ステップを Routine に置き換えるだけ
- **M2 が未完成でも単体で価値が出る** — 「劣化のトレンドが毎朝勝手に見える」状態が先に手に入る
- Routine の登録は Web UI 操作が必要で agent からは実行できない (#90 / #92 と同型) → **needs-human Issue として起票する**。未登録の間も手動起動で同じ手順が回る形を保つ

### D2. 改変対象の境界は「プロンプトの外出し + CI での diff パス検査」で縛る

- `CHAT_SYSTEM_PROMPT` を `workflow.py` から**専用ファイルへ分離**する。これにより (a) 自動 PR の触る範囲が 1 ファイルに確定し、(b) v2 M1-3 の移行と衝突しなくなる
- 自動改善 PR には専用ラベル (`ux-auto-improve`) を付け、**CI が diff のパスを検査**する。許可パス以外の変更が含まれていたら赤にする
- 起票プロンプトにも境界を明記する (ADR 0021 の運用) が、**強制力は CI 側に置く**。子セッションが指示を見落としてもマージされない

### D3. A/B は実環境の外 (CI 上の ai-agent) で回す

A/B の比較対象は**会話文のみ**であり、rubric の U1〜U5 は記録された会話テキストだけで採点できる。したがって:

- CI 上で ai-agent を 2 通り (旧プロンプト / 新プロンプト) 起動し、`/chat` を同一シナリオで N 往復叩いて会話を生成する。**ブラウザも実環境も不要**
- **U6 (レイテンシ) は A/B の採点対象から外す** — プロンプト変更で速度は変わらず、CI 上の実行時間は実環境の体感と無関係なため。レイテンシの監視は従来どおり毎朝のプローブ (実環境) が担う
- 実環境のプロンプトを差し替えない。ai-agent に外部からのプロンプト上書き口を**作らない**

### D4. 判定は「同一シナリオ N=3 の盲検 pairwise + 多数決」

- 新旧それぞれ同一シナリオを **N=3 回**流す (計 6 会話)
- judge に**順序とラベルを伏せて** 3 組の pairwise 判定をさせ、**2 勝以上で勝ち**とする
- 勝った案のみ PR 化。負けた案は Issue にレポートとして残す (ADR 0022)
- N 回に増やすコストは**改善が起動した日だけ**発生する (毎日ではない)

### コストのガード

通常日は「プローブ 1 + 採点 1」で ADR 0022 の数十円/日を維持する。改善が起動した日は「改案 1 + A/B 6 会話 + 盲検 3 判定」が上乗せされるため、**改善の起動頻度に上限を設ける** (初期値: 週 2 回まで)。上限に達した劣化検知は Issue へ積み、次週へ繰り越す。予算アラート (月 ¥3,000 / ADR 0013) は既存のまま最終防波堤として機能する。

## 守るべき資源への到達経路 (全数)

| 資源 | 到達経路 | ガード |
| --- | --- | --- |
| Azure OpenAI (課金) | ①毎朝のプローブ ②毎朝の採点 ③改案生成 ④A/B の 6 会話 ⑤盲検判定 3 回 | 改善の起動頻度上限 (週 2) / 予算アラート 月 ¥3,000 |
| リポジトリ write | 改善子セッションの push / PR 作成 | CI の diff パス検査 (許可外は赤) / ブランチ保護 / **マージは人間** |
| 実環境 dev | 毎朝のプローブのみ (A/B は到達しない — D3) | プローブは読み取り的操作のみ。A/B 用の上書き口を作らないことで経路を増やさない |

## 動作検証 (実装後に何を叩けば「効いている」と言えるか)

「設定した」ではなく振る舞いで書く ([ADR 0018](0018-runtime-verification-in-the-loop.md))。

- **M1.5**: Routine を手動発火させた翌朝、#127 に `ux-judge-score` の JSON ブロックを含むコメントが**人手を介さず 1 件増えている**。runbook の jq がそのコメントを 1 行として抽出できる
- **D2 (境界)**: `ux-auto-improve` ラベルを付けた検証用 PR で、許可パス外のファイルを 1 行変更すると **CI が赤になる**。許可パスのみの変更なら緑になる
- **D3 (実環境不可侵)**: A/B ジョブの実行中に実環境の ai-agent の revision が**変化していない**ことを確認する。ai-agent の API にプロンプト上書きのパラメータが存在しないことを OpenAPI (`docs/api/ai-agent.yaml`) の diff で確認する
- **D4 (判定)**: 新旧に**同一のプロンプト**を入れた対照実験を 1 回流し、勝敗が 3 戦で割れる (= 揺らぎを揺らぎとして扱えている) ことを確認する。ここで一方が 3 連勝するなら判定が揺らぎを拾えていない
- **コスト**: 改善が 1 回走った日の Azure OpenAI 実測コストを記録し、想定オーダー内であることを確認する

## Positive Consequences

- トリガーの入力が実在するようになり、ループが人手なしで起点に到達する
- 自動 PR の破壊範囲が仕組みで有界になる (約束依存でなくなる)
- A/B が実環境から切り離されるため、実験中に PO が実験台にならず、ai-agent への新しい扉も増えない
- 揺らぎ耐性を対照実験で検証できる形になり、「judge の甘さ」を構造で点検できる

## Negative Consequences

- ステップが 1 つ増える (M1.5) ため、M2 の完成は後ろにずれる。ただし M1.5 単体で「トレンドが見える」価値が先に出る
- Routine 登録が人間の宿題として 1 件増える (#90 / #92 に続き 3 件目)
- A/B が CI 上の ai-agent を使うため、**実環境固有の要因 (実際のモデルデプロイ差・RAG の内容差) は A/B に反映されない**。実環境での効果確認は翌朝のプローブに委ねる
- プロンプトの外出しは v2 M1-3 の移行範囲に軽微な変更を与える (移行時に参照元が 1 つ増える)

## Considered Options (却下したもの)

- **M1.5 を切らず M2 に含める** — 往復は 1 回で済むが、壊れたときに「採点の無人化」と「改善ループ」のどちらが原因か切り分けられない。ADR 0022/0016 で繰り返している「変化は 1 度に 1 種類」に反する
- **v2 M1-3 の完了を待つ** — 衝突は消えるが、体験改善が v2 移行の完了までブロックされる。#119 (応答が浅い) が最優先である以上、待つコストが高い
- **境界を起票プロンプトの指示だけで縛る** — 工事 0 だが約束依存。#86 で「門を 1 枚足したが別経路が開いていた」実例があり、規律に依存しない設計を選ぶ (ADR 0014 の Decision Driver)
- **A/B を実環境のプロンプト差し替えで行う** — 実装は素直だが、PO が実験台になり、ai-agent に上書き口という扉が増える (発見 3)
- **A/B をシナリオ 1 本 1 回で行う** — 最も安いが、改案の効果と LLM の揺らぎが区別できず、負けるべき案が勝つ
