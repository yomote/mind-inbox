# 0021. 親セッションを PM ハブにして、並行作業は子セッションへ分配する (hub-and-spoke)

- Status: Accepted (debrief #3, 2026-08-08)
- Date: 2026-08-08
- Deciders: omoteforlab
- Consulted: —
- Informed: —

Technical Story: 2026-08-08 の status セッションで、user 指示により親セッションから 2 つの子セッション (#107 デプロイ修正 / PR #113 + #112 認証まわり) を分配起動した。user から「これをデフォルトの対話形態にしたい — 個別に報告が来ると分からなくなるので親に集約してほしい」との明示要望。

## Context and Problem Statement

開発が複数ワークストリーム (インフラ CD / 認証 E2E / frontend UX など) で並行するようになり、Claude Code Remote のセッションを同時に複数走らせる場面が増えた。しかし現状はセッション間の関係が規約化されておらず、次の問題がある:

- **報告の分散** — 各セッションがそれぞれ user に報告し、user はどのセッションで何が起きているかを追い切れない (po-feedback 初回で実測された「何を見ればいいか分からない」問題の再演)
- **スコープ衝突** — 並行セッションが同じファイルを触って conflict する事故を、都度の注意でしか防げない
- **文脈の断絶** — 全体状況 (優先度・依存関係・「次の一手」) を持っているのは status を引いた親セッションだが、その文脈が子の起票に引き継がれる保証がない

user (PO) の対話窓口を 1 本に集約し、並行実行を規約化する必要がある。

## Decision Drivers

- **窓口の一元化** — user が見る場所・話す場所を 1 つにする (ADR 0020「溜まり場の一元化」と同じ思想)
- **並行性の確保** — 独立した作業は同時に進む (直列化で遅くしない)
- **衝突の構造的予防** — 「気をつける」ではなく起票時のスコープ境界で防ぐ
- **既存機構の再利用** — Issues = 実行状態 (ADR 0011)、needs-human キュー (ADR 0020)、PR 追従規約をそのまま使う

## Considered Options

- Option A: **親セッション = PM ハブ (hub-and-spoke)** — user は親とだけ話し、親が子セッションへ分配・集約する
- Option B: フラット運用 — user が必要に応じて各セッションを直接立てて直接会話する (現状)
- Option C: 全部 1 セッション直列 — 並行させず 1 本のセッションで順にやる

## Decision Outcome

Chosen option: **"Option A"**。既定の対話形態を次の規約で定める:

1. **user の対話窓口は親 (PM) セッション 1 本** — 進捗確認・優先度判断・作業指示は親に対して行う。親は PM/PjM として全体状況 (`/status`) を把握し、次の一手を提案する
2. **並行できる作業は親が子セッションへ分配する** — 分配の条件は「Issue 単位で独立していて、触るファイル領域が重ならない」こと。起票プロンプトには必ず (a) 対象 Issue/PR 番号、(b) 完遂条件 (PR merge まで追従 + subscribe_pr_activity)、(c) **触ってはいけないファイル境界** (並行セッションとの衝突予防)、(d) CLAUDE.md 規約への参照、を含める
3. **子は user に直接報告しない** — 子の成果は PR / Issue コメント / needs-human Issue (ADR 0020) に残す。user への状況報告は親が `/status` + セッション一覧 + PR 状態から**都度ライブに集約**する (親の記憶ではなく GitHub の状態を真実とする — ADR 0011)。セッション一覧の取得手段は環境依存 (例: Claude Code Remote の `list_sessions`) — 規約が求めるのは「集約はライブ状態から」であり特定ツールではない
4. **親は子を放置しない** — 分配後は定期チェックインを仕込み (予約起床の機構は環境依存。例: `send_later` / `ScheduleWakeup`)、停滞・ブロック (needs-human 積み・CI 赤の放置) を検知したら user へまとめて報告する
5. **例外は明示的に** — user が特定セッションと直接話すのは自由 (規約は既定であって強制ではない)。また設計判断を伴う作業 (design-gate 対象) は子に分配せず、親で user とゲートを通してから分配する
6. **親は一目で分かる名前にし、常に 1 本** — 親セッションのタイトルは `[PM]` 接頭辞 + 開始日で命名する (例: `[PM] Mind Inbox ハブ (2026-08-08〜)`)。user はセッション一覧で `[PM]` を探せばよく、それ以外のセッションは基本見なくてよい
7. **親は使い捨てローテーション** — 長寿セッションはコンテキスト要約の劣化で集約品質が落ちるため、親は debrief 等の節目、またはコンテキスト劣化を自覚した時点で**次代の親セッションを自ら起動して交代**する。引き継ぎ文書は作らない — 状態は GitHub にあり、新親は `/status` で全体像を復元する (規約 3 と同じ原則)。旧親はタイトルを `[PM-retired]` に変えて archive する
8. **親は開発しない** — 親の仕事は状況集約 / 起票と分配 / user との調整 (design-gate・debrief・優先度判断) / プロセス docs (ADR・CLAUDE.md・skill) の編集まで。**プロダクトコード・テスト・IaC の変更は必ず子セッションへ分配する**

### Positive Consequences

- user の認知負荷が「N セッションの監視」から「親 1 本との対話」に下がる。ADR 0020 の「🙋 あなたの番」集約と合流し、見る場所が 1 つになる
- スコープ境界の明示が起票の必須項目になり、並行作業の conflict が構造的に減る
- 分配時に親の全体文脈 (優先度・依存・関連 ADR) がプロンプトに焼き込まれ、子の手戻りが減る

### Negative Consequences

- 親セッションが単一障害点になる — 親のコンテキストが長大化・要約劣化した場合、集約品質が落ちる。緩和: 親は状態を記憶に持たず毎回 GitHub から引き (ADR 0011 と同じ原則)、規約 7 の使い捨てローテーションで定期的に新品コンテキストへ交代する
- 報告のリアルタイム性は下がる (子の完了を user が知るのは親のチェックインか user の問い合わせ時)。緩和: 重要イベント (release-gate 級・ブロッカー) は needs-human Issue に積まれるため取りこぼさない
- 親↔子の直接メッセージングは環境依存 (現状は GitHub 状態経由が確実)。規約の本質は「窓口 1 本 + GitHub が真実」でありツールに依存しない

## Pros and Cons of the Options

### Option A: 親 = PM ハブ (採用)

- Good, because 窓口・溜まり場・見る場所の一元化という既存方針 (ADR 0011/0020) の自然な延長
- Good, because 並行性を保ったまま user の認知負荷だけ下げる
- Bad, because 親セッションの運用規律 (チェックイン・ライブ集約) に依存する

### Option B: フラット運用 (現状)

- Good, because 仕組みが不要で、各セッションと直接話せる
- Bad, because 報告が分散し、user が「どこで何が起きているか」を追う必要がある (実測済みの破綻)
- Bad, because スコープ衝突の予防が個々のセッション起票者の注意力任せになる

### Option C: 1 セッション直列

- Good, because 集約も衝突予防も自明
- Bad, because 独立作業まで直列化され、スループットが最悪になる
- Bad, because 長大セッションのコンテキスト劣化がそのまま全作業の品質劣化になる
