# 0015. システムの能動化 — ガードレール付きプロアクティブ・エージェントワークフローを解禁する (思想転換)

- Status: Accepted (design-gate #1, 2026-08-06)
- Date: 2026-08-06
- Deciders: omoteforlab
- Consulted: —
- Informed: —

Technical Story: [`requirements.md §2.2`](../design/requirements.md) が「AI による状況ウォッチ & プロアクティブなアナウンス / nudge は、思想転換を ADR で明示判断した上で設計する」と定めた、**その ADR**。design-gate セッション (2026-08-06) での user の要望表明を受けて起案。

## Context and Problem Statement

concept_deck §4 は「Plan 提案は毎回必須にしない / 望まれたときだけ次の一歩」という**プロアクティブ抑制**を v1 の設計思想とし、requirements §4 も v1 の AI の振る舞いを**受動的** (ユーザー操作に応答) と明記した。v1 の蓄積基盤 (Problem 中心 2層, ADR 0007) が Phase A〜C で実装された今、次フェーズの方向を決める必要がある。

user の要望は明確になった: **AI には能動的になってほしい**。(1) 暗黙知を引き出す構造 (溜まった Problem を素材に AI 側から深掘りが来る)、(2) 外部データとの連携で「脳内の悩みが外界とつながって展開される」体験、(3) 適切なナレッジ活用 (吐き出しの構造化保存と RAG)。ただし副作用のある操作は human-in-the-loop 承認を必須とする。抑制思想をどこまで残し、どこを転換するかを決める。

## Decision Drivers

- **暗黙知の引き出し** — 蓄積が「受動的に見返せる」だけでは死蔵する。AI からの深掘りが再吐き出しを誘発する構造にしたい
- **外界との接続** — 悩みが外部データ (予定・活動・知識) と繋がって展開される世界観 (user の中核要望)
- **安心と自律の維持** — 押し付けない・急かさないという concept_deck の価値は捨てない。能動化が「うるさい通知アプリ」に堕ちたら本末転倒
- **HITL の堅持** — 副作用 (外部送信・通知・データ変更) は人間の承認が最後の歯止め
- **v1 基盤の上に載る** — Problem / Mention の蓄積とトリアージ (可逆な事後修正) を素材・受け皿として使う

## Considered Options

- Option A: **現状維持** — 受動のまま。能動化しない
- Option B: **全面能動化** — 制約なしに AI が通知・操作まで自動で行う
- Option C: **ガードレール付き能動化** — システムは能動化するが、出力の届け方と副作用に構造的な歯止めを置く

## Decision Outcome

Chosen option: **"Option C" (ガードレール付き能動化)**。requirements §4 の脚注どおり「アクターが増える」のではなく「**システムが能動化する**」変更として設計し、抑制思想は「能動化しない」から「**能動でも押し付けない**」に転換する。

ワークフローは 3 系統に整理する:

| 系統 | 内容 | 新規性 |
| --- | --- | --- |
| **リアクティブ** | 対話 / 抽出+グルーピング / プラン生成 (現行) | 継続 |
| **プロアクティブ (内部整理)** | 定期棚卸し・再グルーピング・ダイジェスト生成 | 新規。可逆な内部操作 |
| **プロアクティブ (働きかけ)** | ウォッチ (再出現の増加・放置 Problem・パターン検知) → **気づきカード** / 暗黙知を引き出す**深掘り質問の生成** | 新規。ガードレール対象 |

ガードレールは 3 つ:

1. **副作用の HITL 承認** — 外部への送信・通知・ユーザーデータの非可逆変更は承認必須 (現行 `requiresApproval` 系譜の継続)
2. **プッシュで届き、受信箱に残る** — 気づき・深掘り質問はプッシュ通知で能動的に届ける (design-gate #1 での user 判断: 「受信箱で待つのみ」案を退けプッシュ既定を選択)。「押し付けない」の担保は届け方の抑制ではなく、**頻度予算・静穏時間・カテゴリ別オンオフをユーザー設定に置く**ことで行い、通知の実体は常に受信箱にも残って後から読み返せる
3. **内部整理は可逆に** — 自動再グルーピング等は事後トリアージ (ADR 0007) で全て取り消せる操作に限る

**ナレッジ層**: Mention / Problem を embedding で索引化し (Phase 2 のグルーピング精度向上と同一基盤)、深掘り・ウォッチ・RAG の共通素材にする。外部データは read-only ツール接続から始める。

**スコープ外 (実装計画で判断)**: 外部コネクタの選定と課金を伴うリソース追加 (Azure AI Search 等)・通知チャネルの実装・頻度予算の既定値。オーケストレーション基盤の選定は [ADR 0016](0016-ai-agent-orchestration-on-maf.md) に分離。

Option A は user の中核要望と requirements §2.2 の構想自体を放棄する。Option B は concept_deck の安心・自律の価値を壊し、信頼されないアシスタントになる。

### Positive Consequences

- 蓄積 (v1) が「引き出される」動線を得て、暗黙知の外化という中核価値に接続する
- 能動化の範囲が 3 系統 + 3 ガードレールとして明文化され、以後の機能追加の判断基準になる
- 内部整理はトリアージで可逆、外部副作用は承認、と安全側の非対称性が構造で保証される

### Negative Consequences

- 気づき・深掘りの品質が悪いと「的外れな AI」体験になる (品質はワークフロー実装とナレッジ層の精度に依存)
- プッシュ既定のため、頻度予算の初期値を誤ると通知疲れのリスクが受信箱のみ案より高い (ユーザー設定と予算チューニングで緩和)
- 受信箱・設定 UI など、v1 に無かった UI 面の追加コストが発生する
- スケジュール実行基盤 (定期棚卸し) の運用が増える
- concept_deck §4 の記述と乖離するため、concept_deck 側の追記が必要になる

## Pros and Cons of the Options

### Option A: 現状維持 (受動のみ)

- Good, because 追加コストゼロ・思想の一貫性維持
- Bad, because 蓄積が死蔵し、user の中核要望 (暗黙知の引き出し・外界接続) を放棄する

### Option B: 全面能動化

- Good, because 実装上の制約が最少で「賢い AI」を最速で見せられる
- Bad, because 押し付け・通知疲れで安心の価値を壊す。副作用の歯止めも失う

### Option C: ガードレール付き能動化 (採用)

- Good, because 能動化と「押し付けない」を構造 (受信箱・HITL・可逆性) で両立する
- Good, because v1 の資産 (トリアージ・requiresApproval) がそのままガードレールの実装になる
- Bad, because ワークフロー・受信箱・設定と作るものが増える (段階実装で緩和)
