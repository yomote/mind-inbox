### 3.5 前提の明示 — 仮定を先に置く

> **同一リポジトリのブランチから作る PR では** `pull_request` / `pull_request_review` の workflow 定義自体が PR 側から来ており、この job には引き続き `statuses: write` があります。 (#324)

<!-- -->

> **外部 fork の PR を maintainer が merge queue に入れた場合**、`merge_group` は fork の `pull_request` 実行とは異なり、この workflow で宣言した `pull-requests: write` / `statuses: write` の `GITHUB_TOKEN` を使用します。 (#271)

<!-- -->

> **`--rgs` または `--subs` に複数のデプロイが含まれる場合**、これら scope なしの `find_nodes` 呼び出しは Cartesian product を作る (#217)

### 3.9 再レビューの規律 — これが単発の質より効いている

再レビューのコメントは **必ず冒頭で前回分の解消状況を宣言**する。

> **前回の P2（同じ既存 Problem を ID 単位で数える件）は解消を確認しました。** 一方、preview 後に別タブの `problem.triage({ action: "dismiss" })` などで対象 Problem が削除されてから draft を確定すると… (#286)

<!-- -->

> **前回までの P2 のうち、Problem 単位集計、初回の実績件数・grouping、stub 印、保存データの冪等性、消失対象を再送した際の `new` 維持、初回確定時の最新状態反映は解消を確認しました。** ただし、対象が `resolved` / `shelved` の状態で… (#286)

再提起するときは **必ず「新しい根拠」を明示**する。

> **以前の消失対象に関する P2 が単一 Mention のテストだけでは不十分だったことを示す新しい反例です。** (#286)

<!-- -->

> **前回の P2 は未解消です。新しい根拠として、通知の 4 分後に PO が Issue 本文を編集した場合**、`updated_at` と最新コメントの差が 5 分以下なので、この条件は編集を通知由来の汚染として捨てます。 (#258)

<!-- -->

> **これは今回追加された allowlist から確認できる新しい不整合です。** (#342)

これにより「同じ指摘の繰り返し」ではなく「**反例が毎回強くなる**」形になる。PM 側の対応も毎回具体化する。

### 3.10 テストを指摘対象にする

「テストがない」ではなく「**そのテストは直すべきバグを通す**」を言う。

> **「テストも接頭辞しか検証しないため通過しています」** (#330 — PM 返答「この指摘が一番効きました」)

<!-- -->

> このスタブは非ゼロの終了コードを常に `http_code=000`・空 body にしていますが、応答ヘッダーや本文の途中まで受信してからタイムアウト／切断した場合、実 curl は非ゼロ rc と `200`、部分 body を同時に返します… **この部分応答ケースもスタブへ追加してください。** (#340)

<!-- -->

> **追加テストも PKESK だけの切り詰めしか模していないので、データパケット途中／末尾欠落を追加し**、パケットが完全な境界まで読めたことを検証してください。 (#300)

### 3.11 何を「言わなかった」か

215 件を通して、以下は **1 件もない**:

- スタイル / フォーマット / 命名の指摘
- 「もっと簡潔に書けます」「この抽象化は過剰です」
- 「既存ユーティリティの再実装です」
- PR 本文 / Verification 表 / テンプレート記入の指摘 (軸 C 相当)
- 褒め言葉、総評、LGTM 宣言
- 「検討してください」だけで終わる漠然とした提案 (必ず条件と帰結が付く)

### 4.2 ⭐ 「Codex は拾ったが、既存 rubric の軸には無い」もの — PO が言う「洗練されていない」の正体

#### (1) 宣言と参照面の乖離 (~60 件 = 全体の 28%) ← 最大の欠落

決定・型・既定値・規約を変えたとき、**それを引用している場所がリポジトリ中どこにあるかを実際に探して**、古い主張が残っていることを指摘する。軸 A-3 は「UI 変更で MDX / 運用手順で Runbook」しか見ない。Codex が実際に見た参照面:

README の表 / ADR の索引 / ADR の Status 行 / **他の Accepted ADR の本文** / skill 定義 / agent 定義 / Issue テンプレート / journal / workflow の `permissions` ブロック / CLAUDE.md / AGENTS.md / rubric ファイル自身。

実例 (#315):

> **DELETE_ENTRA_APP の既定値を README でも false にそろえる**
>
> ここでは「破壊系の既定は off」「`DELETE_ENTRA_APP` も既定 off」と説明していますが、**同じ README の環境変数表（29 行目）は既定値を `true` と記載したまま**です。実装は `false` に反転しているため、README を参照した運用者が Entra アプリが削除されると誤認し、撤収後も残ったアプリ登録を見落とす可能性があります。

PM の返答: 「**同じ表の中の 1 行を見落としていました**」「2026-08-11 の journal に自分で書いた教訓を、**同一ファイル内にすら適用しきれていなかった**」

実例 (#251) — rubric ファイル自身が指摘対象になった:

> **Update the active PR-review rubric for the new layers**
>
> The two previously reported template and `CLAUDE.md` inconsistencies are fixed, but when the automated PR reviewer follows `.github/claude/review-rubric.md`, **lines 25 and 57 still require an L2 test for every feature and classify a missing L2 test as a blocker.** This new entry condition deliberately excludes routing, wrappers, and other changes from unit tests, so compliant PRs can now receive false blocking reviews; migrate the active rubric alongside the strategy.

#### (2) 「取れなかったもの」を「異常なし」と読む経路 (~25 件)

軸 B の「例外パス」では全く捉えられない。Codex の対象は:

- `|| true` / `|| echo` が終了コードを 0 に戻す (#222 #290 #279)
- workflow が「全 step skip」でも success (#281 #288 #214)
- 検索の失敗と「見つからなかった」を混同 (#222)
- `--paginate` の複数ページ出力を単一 JSON として読んで例外 → sweep 全体が毎回中断 (#258)

実例 (#222):

> Azure の権限不足や一時的な Graph エラーで `az ad app federated-credential create` が失敗しても、**`|| echo` が終了コードを 0 に戻すため処理が続き**、最後に `AZURE_CLIENT_ID_RO` の登録案内を表示してスクリプト全体も成功終了します。**実際にこのコマンドだけを失敗させると終了コード 0 になり**、利用者は OIDC 資格情報が欠けた ID を登録して、その後の `ops/inspect` が Azure login で失敗するまで不完全な構成に気づけません。

PM の返答: 「**実行して確かめた結果**」の表 + 「**回帰の証拠**: 修正前の `ro.sh` を同じスタブで失敗させると、exit 0 のまま登録案内を表示しました」。さらに「指摘の箇所以外に、**同じ形の握り潰しが 2 つあった**ので一緒に直しました」。

#### (3) テストが差別化できているか (~12 件)

軸 A-1 は「テストが**あるか**」しか問わない。Codex は「**そのテストは、直すべきバグを入れても緑のままか**」を問う。

実例 (#340) — PM の返答が最も雄弁:

> **指摘が正しく、実測で再現しました。しかもこれは私の修正が作り込んだ、元のバグより悪い状態でした。**
> … 原因は、追加したテストが「接続失敗 (rc≠0 かつ body 空)」しか模しておらず、**異常系のスタブが本物の curl より優しかった**ことです。異常系を作るときに「一番厄介な壊れ方」ではなく「**一番書きやすい壊れ方**」を選んでいました。

## Step 5 — Codex の限界 (神格化しないための記録)

### (a) 見えない実環境について、リポジトリのファイルから推論して外した — PR #292

Codex:

> 標準の OIDC 設定は `cicd/scripts/cloud-env/setup-oidc.sh:15` および `docs/runbooks/azure-oidc-cd-setup.md:36` のとおり **Contributor だけです。Contributor は `Microsoft.Authorization/*/Write` を除外するため、Actions 経由の `provision.sh` はここで `AuthorizationFailed` となり**、案内された復旧手順を完遂できません（Contributor の公式ロール定義へのリンク — 収集時に URL を省略）。

PM が device-code で実環境を測った結果:

> **前提は正しく、結論は実環境の実測と食い違います。** … `gha-oidc-mind-inbox-cd` のサブスクリプションスコープの割り当て: **Contributor** (2025-07-05) / **User Access Administrator** (2026-07-07)。**User Access Administrator が後から足されており**、これが `Microsoft.Authorization/*` を持つので… 実環境がそれを別のロールで補っていた、というのが答えでした。

**教訓**: Codex はリポジトリの宣言を実態と同一視する。**クラウド・外部サービスの現況は測れない。** ただしこの指摘は「新規サブスクリプションでは本当に落ちる」という予防的価値が残り、PM は #46 に測定結果を記録した。**外した指摘にも価値があった珍しい例。**

### (b) プラットフォーム挙動を事実誤認した — PR #279

> `cicd/iac/README.md:262-273` では引き続き `az deployment group create --mode Complete` を更新手順として案内しており、**このモードではテンプレートから外した既存の OpenAI role assignment も削除されます**が…

## Step 6 — 総括: このデータで rubric を作れるか

**作れる。** 45 時間・46 PR・215 件は、指摘の**形**を写し取るには十分な量で、しかも:

- **同一の型が 215 回反復されている** (テンプレートが明確に読み取れる)
- **PM 側の返答が全件に付いており、効いたかどうかが本人の言葉で記録されている** (「これが一番効きました」「見落としていました」「私の修正が作り込んだ、元のバグより悪い状態でした」)
- **反証された 3 件があるので、Codex の弱点も実データで押さえられる**

**足りないもの**: 期間が 45 時間しかないので、(i) 大規模リファクタリング PR、(ii) 新機能の初回設計 PR、(iii) 依存更新 PR に対する Codex の振る舞いは観測できていない (dependabot PR は全てレビュー対象外だった)。これらは rubric に書けない。
