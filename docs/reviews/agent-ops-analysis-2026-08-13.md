**構造**: エージェントの能力の可否は **(実行環境 × 時刻) の関数**である。対話セッション / 子セッション / Routine 発火セッションでツール面が違い、プラットフォーム側の更新で日をまたいで変わる。ところが可否は **ADR — 「不変記録」と定義された場所** に書かれ、[誰も再測定しない](../adr/README.md)。結果、**誤った不可能性が制度化され、それを前提にした体制が組まれる**。

現時点で `CLAUDE.md` と ADR に生きている能力の断定を数えると、**再測定日が併記されているものは 1 つも無い** (`SendMessage` / `ListAgents` は使えない / `fire_trigger` は配送されない / `update_trigger` は自分の Routine しか通らない / `create_trigger` に `source_url` を渡す口が無い、等)。**どれも今日は正しいかもしれないし、ADR 0033 と同じ運命かもしれない。区別する手段が無い。**

## Step 3 — 5 つの故障モード (症状ではなく原因)

### F1. 能力の断定が、測定されないまま不変記録に固定される

Step 2 の症状 3 そのもの。**「できない」は事実の報告ではなく、有効期限のある観測である**にもかかわらず、有効期限を書く場所が無い。

### F2. 完遂の最後の一歩が 1 人に集まり、それを外す機構自体が故障している

Step 2 の症状 1。加えて、**故障由来の人待ちと、本当に人にしか押せない人待ちが、同じ `needs-human` ラベルの下に混ざっている**。今朝の当番 tick は「needs-human 19 件、48 時間以上の停滞は 0 件」と正しく報告したが、この 19 件のうち何件が「工場の障害」かは**誰も分けていない**。分けていないので、PO には「宿題が 19 件ある」に見え、エージェント側には「PO 待ちなので触れない」に見える。

### F3. 工場の在庫に上限が無く、撤去する担当がいない

Step 2 の症状 2。新設側には既に規律がある (「自動化を足したら `watchers.json` に 1 行足す。足せないなら作らない」)。**撤去側には何も無い**。[#378](https://github.com/yomote/mind-inbox/issues/378) の未解決欄が名指ししている: 「**減らす提案を誰も出していない**」。

### F4. 測定器の粒度が粗く、赤の意味が読み手ごとに違う

**この調査自身がその実例になった。** `deploy` workflow の直近 30 run は **success 0 / failure 28 / cancelled 2**。この数字だけを見て「デプロイが 30 連敗していて、プロダクトが dev に届いていない」と書きかけた。

最新 run (`31654965441`) の step を開くと違った:

```
12  Provision + deploy (up)                     success   (6m15s)
13  Smoke test（認可と疎通の実測）               success
14  Golden path（相談ユースケースの実測・実 AI） success
15  Golden path scenario（UI 込み E2E・実環境）  failure   ← ここだけ
```

**配信は成功している。赤いのは最後の UI E2E 1 本だけ**である。当番 PM tick は正しく読んでいた (「デプロイも成功、E2E も 4 本中 3 本が緑」)。

つまり `deploy` の conclusion は「**dev に届いたか**」と「**UI が通るか**」を 1 つの色に潰しており、[ADR 0043](../adr/0043-pm-self-driving-mode.md) D1 が一級指標に据えた「dev で触れるようになったもの」を**機械から読めなくしている**。分割は [#305](https://github.com/yomote/mind-inbox/issues/305) が既に提案しているが P2 のまま。

同型が他に 2 件:

- [#381](https://github.com/yomote/mind-inbox/issues/381) — `adr-number-guard` の緑が腐る (PR 作成時の base としか比較しないので、後から main に同じ番号が着地しても緑のまま)
- [#352](https://github.com/yomote/mind-inbox/issues/352) — 代役 judge に自動起動が無く、**沈黙と「指摘なし」が区別できない**

### F5. 規約は読まれていて、守られない

[#378](https://github.com/yomote/mind-inbox/issues/378) の結論:「**失敗 8 件中 5 件が、その窓口がその日に読み・参照し・他人に説明した規約を破っている**」。読んでいないのではない。

したがって **F1〜F4 に対して「新しい規約」を書くのは、6 回目の同じ失敗**になる。対策は既定値・門・データのいずれかに落ちていなければならない。[#351](https://github.com/yomote/mind-inbox/issues/351) がコードレビューについて出した判定基準がそのまま使える — **「機械が探せる形の 1 文にできるか」**。

## Step 4 — スクラムの器は既にある。空なのは中身

PO の「PM セッションがスクラム的に動いてほしい」に対して、**足りないのは儀式ではない**。既に設計され、承認されている:

| スクラムの要素       | このリポジトリでの実体                                                                                                      | 状態                                                                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| プロダクトバックログ | `stream:*` 5 レーン ([ADR 0044](../adr/0044-stream-lanes-as-the-project-map.md))                                            | ✅ 動いている (ただし 73% が工場・インフラ)                                                                                                |
| スプリントゴール     | 週次プロダクト目標の milestone ([ADR 0043](../adr/0043-pm-self-driving-mode.md) D2)                                         | ❓ **実在を確認できない** (Step 1 の「取れなかったもの」)                                                                                  |
| デイリースクラム     | 当番 PM tick (1 日複数回) + 日次ダイジェスト ([ADR 0040](../adr/0040-project-continuity-three-layers.md) D2 / 0043 D4)      | ✅ **動いている。品質も高い** ([#254](https://github.com/yomote/mind-inbox/issues/254) の 08-13 00:26Z レポートは診断の更新まで含めて正確) |
| インクリメント       | 「dev で触れるようになったもの」(ADR 0043 D1)                                                                               | ❌ **機械から読めない** (F4)                                                                                                               |
| レトロスペクティブ   | `debrief` / `po-feedback` skill ([ADR 0014](../adr/0014-design-comprehension-gate-and-debrief.md))                          | ✅ 動いている                                                                                                                              |
| 開発チーム (並行)    | 子セッション + subagent の 2 層 ([ADR 0048](../adr/0048-child-sessions-are-usable-again-with-a-one-way-poke-channel.md) D1) | ⚠️ **道具は動くのに使われていない**                                                                                                        |

最後の行が PO の「自律的に動いてほしい」の核心。[#378](https://github.com/yomote/mind-inbox/issues/378) の失敗 1 と 2 が同じことを別角度から測っている:

- 窓口 PM が起こした子セッションは、PO が「私が破綻する」と言うまで **0 本**
- PO の指摘: 「**タスクを分割して並行でできてないから、結局私が複数セッション切ることになった**」

つまり **PO が手作業でスケーリングを肩代わりしていた**。窓口が実装者になっている構造は [#348](https://github.com/yomote/mind-inbox/issues/348) が既に特定している ([ADR 0033](../adr/0033-parent-implements-via-subagent-when-child-sessions-are-gated.md) で「小さい作業は親が直接書く」に緩めた時点で hub-and-spoke が反転した)。

**一方で、分配が機能した実例も同じ日にある**: 08-12 18:47Z の dependabot PR 7 本の捌き ([#254](https://github.com/yomote/mind-inbox/issues/254#issuecomment-5271272677)) は、窓口から分配された使い捨てセッションが 7 本すべての diff を読み、6 本を実際にインストール・ビルド・起動して検証し、**分配時の見立てが 3 点間違っていたことまで報告して返している**。道具は動く。既定が「自分でやる」になっているだけ。

## Step 5 — 総括: 何を足すべきでないか

この調査から出る対策は、次の 2 つの制約を満たさなければならない。

1. **規約を足さない** (F5)。既定値・CI の門・機械が毎日書き換えるデータ、のいずれかに落ちること
2. **在庫を増やさない** (F3)。1 つ足すなら、何を測って何を消すのかを同時に決めること

そのうえで、5 つの故障モードに対する最小の手当ては次のとおり (判断は [ADR 0054](../adr/0054-agent-ops-mechanisms-for-stalls-and-false-impossibility.md)):

| 故障                  | 手当て                                                                                                   | 新設か既存か                                |
| --------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| F1 能力の誤った制度化 | 能力の断定は**測定日つきの台帳にしか書けない**ようにし、当番 tick が定期的に叩き直す                     | 台帳 1 ファイル + CI 検査 1 本 (**新設**)   |
| F2 人待ちの混線       | `needs-human` に**理由を分ける**。故障由来は PO の宿題ではなく工場の障害として扱う                       | 既存ラベル運用の分割 (**新設ゼロ**)         |
| F3 工場の自己増殖     | WIP 2 枠のうち **1 枠を product 専用**にする + 無痕跡の機構を撤去候補として自動提示                      | 既存の WIP 上限に条件を 1 つ (**新設ゼロ**) |
| F4 赤の意味の粗さ     | `deploy` を「配信」と「UI E2E」に割る ([#305](https://github.com/yomote/mind-inbox/issues/305) を P1 へ) | 既存 Issue の優先度変更 (**新設ゼロ**)      |
| F5 規約が守られない   | 上記をすべて機構で表現する。**規約は 1 行も足さない**                                                    | —                                           |

**この文書自体が F3 のリスクである**ことを記録しておく。分析を 1 本足したので、ADR 0054 の実装で何かを 1 つ以上消せなければ、この調査は症状の一部になる。
