## 1. 目的と原則

### 1.1 ゴール

Mind Inbox は **コーディングエージェント駆動の高速開発** を前提に進める。
テストハーネスのゴールは「カバレッジを高めること」ではなく、次の 3 つを満たすこと:

1. **エージェントが壊した時に必ず気づく** — 静かに通る変更を許さない
2. **ローカルで数十秒以内にフィードバックが返る** — エージェントの試行錯誤サイクルを止めない
3. **失敗時に "どの層が壊れたか" が一目で分かる** — 修正のために原因を探す時間を最小化する

### 1.2 書かない判断 (テストを書かない基準)

「カバレッジを上げる」ではなく「特定の回帰を機械的に止める」のがゴールである以上、**書かないテストを能動的に選ぶ判断** が同じくらい重要。判定は 2 つの問いに集約する:

> **このテストが無いと、どんな回帰が静かに通るか?** — 1 文で書けないなら書かない
>
> **このテストの期待値は、どの仕様から来たか?** — 仕様 (ADR / design doc / 呼び出し元の責務) を指せないなら書かない。**「仕様がないんですけど」と言う** (Issue / PR 本文に書く) のが正しい行動で、実装を読んで期待値を発明するのは間違った行動 (§3.4)

2 つ目は 2026-08-10 に追加した。仕様の無いテストは「実装の写し鏡」になり、偽物の仕様を作ってそれを検証する (実例: 偽 ai-agent に対する受け入れテストが実環境の `/extract` 障害を原理的に踏めなかった)。レイヤ別の応用:

| レイヤ   | 「書く」基準                                                     | 「書かない」基準                                                       |
| -------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 契約     | 異言語間スキーマ整合 (機械的)                                    | 個別フィールドの値検証 (それは単体かスモーク)                          |
| 単体     | **入場条件 (§2.2) を満たすドメインルール**の性質                 | 受け渡し・ルーティング・型の詰め替え・framework wrapper・自明な return |
| スモーク | 外部 (AI / 音声) の**異常系** — 500 / タイムアウト / 壊れた JSON | 正常系の網羅 (それは E2E のゴールデンパスが実物で見る)                 |
| E2E      | ゴールデンパス。実環境でしか出ない壊れ方                         | 本数を増やすこと自体。画面単位の網羅 (UI 仕様は MDX に寄せる)          |

この問いは **Test Issue テンプレ** (`.github/ISSUE_TEMPLATE/test.md`) が着手前に、**テストコードのコメント**が書いた後に持つ。PR 本文には**重要な回帰テストを 1〜3 件だけ**挙げ、全数の理由を並べない (テストが増えるほど PR 本文が肥大し、結論が埋もれるため)。

### 1.3 設計原則

| 原則               | 内容                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **契約集約**       | tRPC の `zod` と AI Agent の `pydantic` は同じ I/O を別言語で書いている。両者の対称性を契約テストで担保                    |
| **偽物を作らない** | 層の境界は「何を偽物にするか」(§2)。**偽物は外部 (AI / 音声) だけ、それもスモークの異常系に限る**                          |
| **性質で書く**     | 単体テストは例ではなくプロパティ (性質) で書くのを既定にする (§3)                                                          |
| **mock 一元化**    | `apps/frontend/src/mockApi.ts` を共通 fixture に。テストごとに別の mock を増やさない                                       |
| **snapshot 最小**  | 境界 (tRPC レスポンス JSON / extract 出力 JSON) のみ。UI snapshot は採用しない                                             |
| **失敗の局所化**   | テスト名に `[契約]` `[単体]` `[スモーク]` `[E2E]` プレフィックスを付け、ログで層を即特定 (移行中の旧プレフィックスは §6.2) |

### 1.4 テスト可能性を設計基準にする

テストは実装の後工程ではなく、**設計の良し悪しを測る計器**として使う。

- **状態・副作用を持つ新モジュールはテストファーストで切る** — 永続化・外部 I/O・時刻・乱数・グローバル状態・ブラウザ API に触るものは、先にテストを書いて I/O 境界を決めてから実装する。後から差し込もうとすると境界が固まっていて手遅れになる
- **テストが書けない構成は、設計の警報として扱う** — 「モックが 5 個要る」「private を触らないと検証できない」「起動しないと 1 行も確かめられない」は、テストの書き方の問題ではなく**依存の向きと責務の置き場所**の問題。テストを通すための小細工ではなく、設計を見直す合図にする
- ただし §1.2 と矛盾させない: テスト可能性のために**書く必要のないテストを増やさない**。増やすのは設計の見直しであって、テスト本数ではない

根拠: 2026-08 の保守性調査 (epic #135) で、テストが効いている層ほど構造が良く、**テストが物理的に書けなかった frontend にだけ状態と副作用が集中**していた。テストを要求されない場所に負債が溜まる。

### 1.5 なぜ 4 層か — 2026-08-10 の実測

直近 54 コミット中、修正は 20 件。壊れ方で分類するとこうなった。

| 壊れ方                          | 件数        |
| ------------------------------- | ----------- |
| **テスト・CI 自身の欠陥**       | **9 (45%)** |
| 実環境の設定・実行条件          | 3           |
| デプロイ機構                    | 3           |
| 無音失敗 (エラーが握り潰される) | 2           |
| 導線・仕様乖離                  | 3           |

**修正の 45% がテスト自身の保守だった。** そして単体テストが捕まえた実バグは記録上ほぼゼロ。維持コストは下の層に集中し、実績は上の層 (実環境) にしかなかった。理由は 3 つ:

1. このプロダクトは**ロジックが薄く結線が厚い** — 価値のほとんどが「他人のものを繋いだ継ぎ目」にある
2. LLM が絡むと正しさが単体で定義できず、無理に単体化すると**偽物を作ってそれを検証する**ことになる (L3-real が偽 ai-agent で走り、実環境の `/extract` 障害を原理的に踏めなかったのが実例)
3. ピラミッドは「下ほど維持が安い」を前提にするが、ここでは**上が一番安定し、中間 (モック E2E) が一番よく壊れる**

だからテストピラミッドを捨て、**「何を偽物にするか」で層を切り直した**のが §2 の 4 層。

## 2. テスト階層 — 4 層を「何を偽物にするか」で切る

```text
┌──────────────┬────────────────────┬──────────────────────────────────┐
│ 層           │ 偽物にするもの       │ ここでやること                     │
├──────────────┼────────────────────┼──────────────────────────────────┤
│ 契約テスト    │ 何も動かさない       │ 2 言語 (zod/pydantic) の定義のズレ │
│ 単体テスト    │ 何も偽物にしない     │ 組み合わせ。BFF のドメインルールだけ │
│ スモークテスト │ 外部だけ (AI/音声)  │ 異常系。500/タイムアウト/壊れた JSON │
│ E2E テスト   │ 何も偽物にしない     │ ゴールデンパス (実環境)。本数を増やさない │
└──────────────┴────────────────────┴──────────────────────────────────┘
```

**層ごとに役割が重複しないように書く**。同じことを 2 つの層で書かない。

### 2.1 契約テスト

| 項目               | 内容                                                                                                                                                                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **目的**           | BFF と AI Agent が同じ I/O を別言語で書いているため、片側だけ変更されても気づけるようにする                                                                                                                                             |
| **対象**           | ai-agent の全エンドポイント (`/chat` `/chat/stream` `/extract` `/plan` `/approve`) の I/O。BFF 側の真実は `apps/bff/src/clients/aiAgentContracts.ts` + `apps/bff/src/trpc/domain.ts` の zod、ai-agent 側は `app/schemas.py` の pydantic |
| **フレームワーク** | TS スクリプト + JSON Schema diff (`apps/bff/scripts/contract-check.mjs` / 比較器は `apps/bff/src/contract/schemaDiff.ts`)                                                                                                               |
| **書き方の指針**   | zod と pydantic からそれぞれ JSON Schema を生成し、**ネストを再帰展開したフィールドパス** (`items[].mention.affect.valence`) 単位で 型 / nullable / 欠落可能性 / enum メンバ集合 を比較。差分があれば fail                              |
| **非ゴール**       | フィールドの値の妥当性。数値の min/max・description などの注釈差、camelCase↔snake_case・`Optional[T]`↔`z.nullable()` の表現差は**意図的に無視**する (false positive を出すと誰も直さなくなる)                                           |
| **実行コマンド**   | `npm run test:contract` (比較器自身の回帰は `apps/bff/src/contract/schemaDiff.test.ts` が守る)                                                                                                                                          |

### 2.2 単体テスト

| 項目               | 内容                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **目的**           | 「壊れても例外が出ず、データが静かに間違う」ドメインルールの正しさを固定する                                                                                              |
| **対象**           | **入場条件 (下記) を満たすものだけ**。BFF のドメインルール (併合 / 状態遷移 / 言及回数の導出 / タイトル導出 / 文分割 / 失敗種別の振り分け / 重複除去 / stub に落ちる境界) |
| **フレームワーク** | TS: vitest (+ fast-check / §3) / Python: pytest (+ hypothesis)                                                                                                            |
| **書き方の指針**   | **例ではなく性質 (プロパティ) で書くのを既定にする** (§3)。I/O は in-memory のみ。ネットワーク / ファイル / DB を触らない                                                 |
| **非ゴール**       | 受け渡し・ルーティング・型の詰め替え。外部依存をモックした「結合フロー」の検証 (旧 L2 — 正常系は E2E、異常系はスモークへ)                                                 |
| **実行コマンド**   | `npm run test:fast` (= `test:bff` / `test:frontend` / `test:python` / `test:scripts` を並列)                                                                              |

#### 単体テストの入場条件

> **単体テストを書いてよいのは「壊れても例外が出ず、データが静かに間違う」ところだけ。**
> 受け渡し・ルーティング・型の詰め替えには書かない。

この条件に当たるのは BFF のドメインルール (上の対象欄)。これらは `domain/` に切り出し、**テスト対象がファイルと 1 対 1 になる**ようにする (切り出しは移行の残作業 / §6.5)。

**大きく失敗するものには単体テストを書かない。** 例: 2026-08-10 の `/extract` 500 (`API version not supported`) は 400 を返して派手に落ちるので、この条件に当たらない。守るのは実環境の通し (E2E のゴールデンパス) の担当であり、実際にそれが捕まえた。

### 2.3 スモークテスト

| 項目               | 内容                                                                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **目的**           | 外部 (AI / 音声) が**壊れた時**にプロダクトが沈黙しないことを保証する。UI とバックエンドの実配線は本物のまま、外部の故障だけを注入する                                      |
| **対象**           | 外部依存の異常系: 500 / タイムアウト / 壊れた JSON / 空応答。通信失敗時に UI が沈黙しないこと                                                                               |
| **フレームワーク** | Playwright (chromium)。`apps/frontend/e2e-uc/` (代表: `failure-modes.spec.ts`)                                                                                              |
| **起動の仕方**     | 3 プロセス: ai-agent ダブル (`e2e-uc/fake-ai-agent.mjs`) → 実 BFF (`apps/bff/scripts/local-server.mjs`) → **`VITE_USE_MOCK` を渡さない** production ビルドの `vite preview` |
| **偽物**           | **ai-agent ダブルだけ** (故障を決定的に注入するため)。フロントの api 層 → tRPC → BFF router → Problem リポジトリはすべて本物                                                |
| **非ゴール**       | 正常系ユースケースの受け入れ判定 (偽 AI に対する受け入れは受け入れの意味を持たない — E2E へ / §6.4)。実 LLM の精度 / 実 VOICEVOX の音声 / Entra の実ログイン                |
| **実行コマンド**   | `pnpm --dir apps/frontend test:e2e:uc`                                                                                                                                      |
| **所有**           | 異常系の追加は**故障モードを増やした実装者**。受け入れ観点の創出は qa-reviewer ([ADR 0019](../adr/0019-independent-judge-agents-security-qa-release.md))                    |

> **注意 (名前の衝突)**: 旧階層の「L4 smoke」(`cicd/scripts/smoke-test/smoke-test.sh` = 実環境疎通) は
> この層では**ない**。あれは実環境検証なので新 4 層では **E2E テスト側** (§2.4 の前段) に属する。

### 2.4 E2E テスト

| 項目               | 内容                                                                                                                                                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **目的**           | **実環境 (dev) で実 AI・実ストレージ・実認証を通す**。「mock は緑なのに実環境で動かない」を構造的に潰す最終防衛線であり、UC 受け入れの引き継ぎ先 ([ADR 0032](../adr/0032-use-case-acceptance-tests-against-real-wiring.md) の見直し / §6.4) |
| **対象**           | ゴールデンパス (相談 → 抽出 → 一覧) + 認可・疎通 + 永続化。**本数を増やさない**                                                                                                                                                             |
| **実体**           | `cicd/scripts/smoke-test/smoke-test.sh` (認可と疎通) → `golden-path.sh` (API 通し・実 AI) → UI 込みシナリオ (デプロイ済み実 SWA を Playwright で操作) → `persistence-probe.sh`                                                              |
| **実行タイミング** | deploy 後 (`.github/workflows/deploy.yml`) + 毎朝の定期実行 (`golden-path-monitor.yml` / 記録は Issue #162、評価は ux-eval)                                                                                                                 |
| **非ゴール**       | 画面単位の網羅 (UI 仕様は MDX が真実 / [ADR 0005](../adr/0005-mdx-ui-spec-as-truth.md))。1 実行に実費と時間がかかる層なので、例の列挙は下の層に置く                                                                                         |
| **書き方の指針**   | 「設定したか」ではなく**振る舞い**を実測する ([ADR 0018](../adr/0018-runtime-verification-in-the-loop.md))。落ちたら Issue が立つ (沈黙と正常を区別する / watchers.json)                                                                    |

**未決 (PO 裁定待ち)**: UC-02〜05 をどこまで E2E に載せるか。「UC ごとに 1 本」なのか「代表 1 本 + 残りは仕様レビュー」なのかは決めていない。ここが決まるまで旧 L3-real の UC spec は消さない (§6.4)。

## 3. プロパティベーステスト

単体テストは**例ではなく性質で書く**のを既定にする。道具は TypeScript が
[`fast-check`](https://fast-check.dev/) (vitest と同居)、Python が `hypothesis`。
1 本目の実例: `apps/bff/src/audio/sentences.property.test.ts` (TTS 文分割)。

### 3.1 いつ使う

- **単体テストの入場条件 (§2.2) を満たす対象には、まずプロパティを検討する**。「静かに間違うデータ」はプロパティが最も強い領域 — 例を並べる代わりに性質を書けば、組み合わせは道具が探す
- 例ベースのテストを禁止はしない。**境界の意図を文書化する少数の例** (「この入力はこう割れる」) はプロパティと補完関係にある。ただし例を 10 個並べて網羅した気になるくらいなら性質 1 つを書く
- **プロパティは仕様が無いと書けない。** これは制約ではなく目的 — 例を書くテストは仕様が無くても書けてしまい、実装の写し鏡 (偽物の仕様) を作る。プロパティを既定にすることで「仕様がないならテストしない、無いと言う」が強制される

### 3.2 プロパティの見つけ方

実装を読んで「今こう動く」を性質にしてはいけない (それは実装の写し鏡で、リファクタの邪魔だけして本番のバグを止めない)。**仕様の出どころ (ADR / design doc / 呼び出し元が何に依存しているか) から性質を導き、出どころをテストコメントに書く**。定番の型:

| 型                   | 問い                                                | このリポジトリでの例                                                                 |
| -------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **往復 (roundtrip)** | 変換して戻すと元に戻るか / 内容が保存されるか       | 文分割: 分割の連結は読み上げ内容 (非空白文字) を失わない                             |
| **不変量**           | どんな入力でも常に成り立つ制約は何か                | `mentionCount` は常に `mentions` の長さと等しい / タイトルは 26 字以下で空にならない |
| **冪等**             | もう一度適用しても変わらないか                      | 分割済みの文を再分割しても変わらない (キャッシュキーがズレない)                      |
| **単調性・安定性**   | 入力が伸びた/増えた時、確定済みの結果は変わらないか | ストリーミング途中で確定した文は、最終テキストの分割にそのまま現れる                 |
| **モデル比較**       | 遅くて自明な参照実装と一致するか                    | 併合: 同じ困りごとを 2 回抽出しても Problem の総数は増えない                         |

### 3.3 fast-check の流儀

- `fc.assert(fc.property(arb, (input) => { expect(...) }))` を vitest の `it` 内に置く。プロパティ 1 つ = `it` 1 つ (失敗時にどの性質が壊れたか名前で分かるように)
- **arbitrary は入力ドメインを狭めすぎない**。対象が意味を持つ文字・値 (文分割なら区切り記号・空白・改行・通常文字の混合) を `fc.constantFrom` 等で混ぜ、境界が自然に生成されるようにする。「都合のいい入力」だけを生成すると例テストと同じになる
- 失敗時は fast-check が**最小反例 (shrinking) と再現 seed** を出力する。直したら、その反例を**例ベースのテストとして固定化**してから修正する (バグ修正の再現テスト / §4.2 と同じ運用)
- 実行回数は既定 (100 runs) から始める。遅くなったら `numRuns` を絞るのではなく、まず対象が単体の入場条件を満たしているか (I/O が in-memory だけか) を疑う

### 3.4 プロパティが書けないとき

書けない理由で行動が分かれる。**どちらの場合も、黙って例テストに逃げない。**

- **仕様が無いから書けない** → テストを書かず、**「仕様がない」と言う** (担当 Issue / PR 本文に明記)。仕様を決めるのは PO / design doc であって、テストコードではない
- **仕様はあるが性質の形にできない** (例が本質的な場合: 特定入力との対応が仕様そのもの) → 例ベースで書き、**参照した仕様をコメントに書く**
- **調べたら実装が仕様の言明より弱かった** (例: 「連結すると元に戻る」は空白のみ断片の破棄仕様と両立しない) → 実装に合わせて性質を弱めたことを**テストコメントと PR 本文に残す**。仕様側を直すべきかは PO / debrief に回す

## 4. 実装タイミング (いつ書くか)

### 4.1 新機能追加時

| 変更の性質                              | 書くもの                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------- |
| ドメインルールの追加・変更 (入場条件内) | **単体** (プロパティ優先 / §3)                                            |
| BFF と AI Agent をまたぐ I/O の変更     | **契約** (zod / pydantic 両側)                                            |
| 外部依存の故障モードが増える            | **スモーク** (異常系を `failure-modes` に追加)                            |
| ゴールデンパスの形が変わる              | **E2E** の該当 hop を更新 (新規に本数を増やさない)                        |
| 受け渡し・ルーティングだけの変更        | **テストは書かない** (§1.2)。動作検証は PR の Verification 欄で実測を貼る |

### 4.2 バグ修正時

**バグ修正 PR には必ず再現テストを 1 本入れる** — ただし再現できる層が新 4 層に**ある場合**。書く層は「最も再現コストが低い層」を選ぶ:

```text
バグ報告
  │
  ├─ データが静かに間違う (例外なし)? ── Yes → 単体で再現 (可能ならプロパティの反例を固定化)
  │       │ No
  ├─ スキーマの言語間ズレ? ──────────── Yes → 契約で再現
  │       │ No
  ├─ 外部の故障への応答が壊れた? ────── Yes → スモークで再現 (故障注入)
  │       │ No
  └─ 実環境でしか再現しない?
          Yes → E2E (ゴールデンパスの hop / プローブ) で再現。
                hop に載らない一過性の環境事故は、再現テストより
                「落ちたら Issue が立つ」導線 (watchers.json) の確認を優先
```

どの層でも再現できない場合は、**その旨を PR に書く** (再現テストの不在を黙って通さない)。

### 4.3 リファクタリング時

- **既存テストを緑のまま動かす** ことが成功条件
- テストを書き換える必要がある = リファクタの粒度が大きすぎる可能性。分割を検討
- snapshot を更新する必要が出たら、**必ず差分を目視レビュー**してから commit
- プロパティテストはリファクタ耐性が高い (実装ではなく性質に結合しているため)。リファクタでプロパティが落ちたら、それは粒度ではなく**挙動が変わった**合図

## 5. 実行タイミングと CI

| タイミング                 | 走る層                                                      | 失敗時の挙動             |
| -------------------------- | ----------------------------------------------------------- | ------------------------ |
| **ローカル (PR を出す前)** | 契約 + 単体 (`npm run test:contract` / `npm run test:fast`) | 直してから出す           |
| **PR push (CI)**           | 契約 + 単体 + スモーク (+ 移行中は旧 L3 mock)               | マージブロック           |
| **deploy 後 (dev)**        | E2E (smoke-test → golden-path → UI シナリオ)                | Issue が立つ / 自動 down |
| **毎朝 (定期)**            | E2E (golden-path-monitor → ux-eval)                         | Issue / status page      |

- エージェントは **最後に `npm run test:fast` を 1 回叩いてから PR を出す** (CLAUDE.md の要求)
- pre-commit は**重くしない** (単体の一部 or 無し)。重いチェックは CI に任せる
- CI (`.github/workflows/test.yml`) は各層を `continue-on-error` で流して最後に集計し、レイヤ別 pass/fail を Step Summary と PR の sticky comment に出す (「契約が落ちたから単体の状況が見えない」を防ぐ)
- **移行中の注意**: test.yml にはまだ旧 L3 mock E2E (`npm run test:e2e`) が残っている。廃止 Issue (§6.3) が完了するまでは**existing のまま走らせ、緑を維持する** (消す順序を間違えると検知の穴が先に開く)
- VOICEVOX wrapper の単体は placeholder (`echo + exit 0` / #2) のまま。placeholder が残っている限り CI の pass 表示は「通った」ではなく「まだ何も見ていない」を意味する

### 6.2 テスト名プレフィックス

- **新規・変更するテストは新プレフィックスを付ける**: `[契約]` / `[単体]` / `[スモーク]` / `[E2E]` (層の名前をそのまま使う。翻訳表を要る英字 3 文字などにしない)
- 対応: `[L0]` → `[契約]`、`[L1]` `[L2]` → `[単体]`、`[L3]` → 廃止層 (リネームせず削除 Issue で扱う)、e2e-uc の spec → `[スモーク]`
- **既存テスト名の一括リネームはこの改訂ではやらない**。旧プレフィックスは移行完了まで有効とし、L3 mock E2E の廃止 Issue (§6.3) の完了後に一括置換の Issue を切る (置換は機械的だが、CI ログ・ドキュメントの grep 導線が同時に切り替わるため、廃止と混ぜない)

### 6.3 L3 mock E2E の廃止 — 方針と手順

**方針**: `apps/frontend/e2e/` の mock ビルド E2E は廃止する。実環境 E2E が同じことをより強く見ており、固有の価値は「デプロイ前に気づける」だけで、中間層としての維持費 (直近実測で最も壊れた層 / §1.5) に見合わない。

**ただしこの doc の改訂ではテストを 1 本も消していない。** 削除は「消すと何が検知できなくなるか」の網羅確認を伴うため、**別 Issue** (PM が起票 / 削除対象 10 テストの一覧と検知能力の棚卸しを本文に含む) で行う。手順:

1. 削除対象の各テストについて「消すと何が検知できなくなるか」と新層でのカバー先を確認する (Issue 本文の表)
2. カバー先が無く価値が残るもの (例: 認証ゲートの #112 事故クラス、旧導線の非表示) は、**削除ではなく移設** (スモーク or E2E の hop) を先に行う
3. spec 削除と同時に `test.yml` から `npm run test:e2e` step と関連 npm scripts を落とす (§5 の移行中注意も消す)
4. 完了後に旧プレフィックス一括リネーム Issue (§6.2) へ進む

### 6.4 スモークテストの範囲 — 旧 L3-real ([ADR 0032](../adr/0032-use-case-acceptance-tests-against-real-wiring.md)) との整合

これは改称ではなく **L3-real の役割の縮小**である。ADR 0032 (Accepted) は L3-real を「UC-01〜05 の受け入れ層」と定義したが、偽 ai-agent に対する受け入れ判定は受け入れの意味を持たない (2026-08-10 の `/extract` 500 をこの層は原理的に踏めなかった)。新しいスモークテストは**異常系のみ**を持ち、**UC 受け入れは E2E テスト (実環境) が引き継ぐ**。

- **未決が 2 つ残っている**: (1) UC-02〜05 をどこまで E2E に載せるか (§2.4)、(2) ADR 0032 の Status 遷移 (ADR 0035 Accept の場で `Superseded` にするか範囲を狭める追補にするか)
- **この 2 つが決まるまで、`e2e-uc/` の UC spec (28 本) は消さない** — 縮小の順序を間違えると受け入れが素で消える ([ADR 0035](../adr/0035-role-split-across-agents-and-actions.md) の表でも既決)
- 所有の分界 (「doc の写経 = 実装者 / 基準の創出 = qa-reviewer」/ 報告会 #5 裁定) は縮小後も変えない

## 7. 運用ガイド

### 7.1 エージェントに期待してはいけないこと

- **snapshot を慎重に更新すること** — 機械的に更新する。よって snapshot は最小限
- **テスト全体を見渡して粒度を調整すること** — 渡した範囲しか見ない。粒度はレビュー時に人間が確認
- **暗黙の契約を察すること** — 契約テストで明示する。コメントに頼らない
- **仕様が無い時に立ち止まること** — 例テストは仕様が無くても書けてしまう。だから単体はプロパティを既定にする (§3.1)

### 7.2 PR に何を書くか

PR 本文の構成は [`.github/PULL_REQUEST_TEMPLATE.md`](../../.github/PULL_REQUEST_TEMPLATE.md) が正典 (ここには再掲しない)。PR 本文は**マージ判断の案内板**であり、テスト設計の保管庫ではない:

- **書く**: Verification 表の結果、重要な回帰テスト 1〜3 件、未検証事項、**「仕様が無くてテストしなかった」箇所** (§3.4)
- **書かない**: 全テストの「無いと何が静かに通るか」(→ テストコード側)、実行コマンドの全出力 (→ `<details>` / Actions)
- 出す前に `npm run test:fast` を緑にする

### 7.3 テスト追加 issue を立てるとき

`.github/ISSUE_TEMPLATE/test.md` を使う。テンプレートが要求する項目: 層 (4 層のどれか) / 目的 (どんな回帰を捕まえるか) / 対象 / **あえてテストしないこと** / 完了条件。これにより agent に着手させる前に、人間が「テスト設計」を査収できる。

### 7.4 テストが落ちた時の切り分け順序

```text
落ちたテスト名のプレフィックスを見る (旧プレフィックスの読み替えは §6.2):
  [契約]   → スキーマ不整合。BFF 側 or AI Agent 側のどちらかが先行
  [単体]   → ドメインルールのバグ。該当ファイルだけ見る。
             プロパティの反例が出ていたら、まず反例を例テストに固定化 (§3.3)
  [スモーク] → 外部故障への応答の退行。実 BFF + ai-agent ダブルの結線を見る
  [E2E]    → 実環境のみで再現する問題。デプロイ・env・外部サービスを疑う
```

### 7.5 FAQ — 表で決まらない判断

- **「プロパティと例のどちらで書く?」** → §3.1。性質が言えるならプロパティ、例が本質 (特定入力との対応が仕様) なら例。両方書くなら例は境界の文書化に絞る
- **「これは単体に書いていい?」** → 入場条件 (§2.2) に戻る。「壊れたら派手に落ちる」なら書かない
- **「snapshot を増やしたい」** → §1.3「snapshot 最小」に戻る (境界の JSON 以外で取らない)。代替で assertion を書けないか検討
- **「mock を新規に作りたい」** → §1.3「mock 一元化」。`apps/frontend/src/mockApi.ts` に必要なデータがあるか先に確認。無ければ既存ファイルに追加 (新規ファイルを作らない)
- **「テストが遅い」** → 単体が in-memory だけか確認 (§2.2)。外部やプロセスを触っているなら層を間違えている
