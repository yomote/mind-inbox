## 2. 有効性の評価 — 「1 本入れて確かめる」の答え

**結論: 有効。導入作業そのものが仕様の穴を 3 つ見つけた** (例ベーステストが何ヶ月も緑のまま素通りしていた領域)。

1. **文分割の往復は成り立っていなかった** — 「分割して連結すると元に戻る」を書いた瞬間に反例 (空白のみ断片は捨てられる) が出た。性質候補の文言を「空白を除いた内容の保存」に補正し、[domain_rules.md §1](../design/domain_rules.md) に現行仕様として明文化
2. **タイトルは「26 文字以下」ではなかった** — 実際は 26 + 省略記号 = 27。さらに UTF-16 コードユニット切りなので**絵文字入りの発話でタイトルが壊れる** (「�」表示)。未決として it.fails で固定 → **2026-08-11 PO 裁定「文字境界で安全に切る」で書記素 (grapheme) 境界に確定・修正し、通常の it に昇格** (domain_rules.md §2)
3. **lastMentionedAt の導出が経路で食い違う** — 追記は「新 Mention の createdAt を無条件採用」(過去日時で逆行する)、relink/merge は「max を再計算」。未決として it.fails で固定 → **2026-08-11 PO 裁定「常に全 Mention の createdAt の最大値」で確定・修正し、通常の it に昇格** (domain_rules.md §3)

つまり期待どおり「**プロパティは仕様が無いと書けない**」が働いた: 性質を書こうとする → 仕様が曖昧なことが分かる → 仕様を書く (or 未決として記録する)、のループが 1 周目から回った。

一方で分かった限界:

- **性質候補「併合しても総数が増えない」は BFF の単体プロパティにできない** — 性質の主語が LLM グルーピング (ai-agent の判定品質) だから。BFF 側で言えるのは「existing 指定は Problem を増やさない」という構造的自明だけ。**LLM が絡む性質は E2E / 実環境の担当** — これは strategy.md §1.3 の「偽物を作らない」と同じ判断
- プロパティは**新しい実バグ (クラッシュ級) は見つけていない**。見つけたのは「仕様と実装のズレ・仕様の穴」。このプロダクトでの価値は bug hunting よりも**仕様の明文化を強制する装置**として出ている

## 3. 書き方ガイド (このリポジトリの流儀)

- **性質の根拠となる仕様を先に指す** — テストヘッダに仕様 doc (domain_rules.md / domain_model.md) へのリンクを書く。仕様が無いなら**先に書く** (実装から読み取った現行挙動を「現行仕様」として起こし、判断が要る点は「未決」と明示)。テストが仕様を発明しない
- **テスト名は `[単体]` + 日本語の性質文** (プレフィックスは strategy.md §6.2 / 4 層改訂後の新名称)。「無いと何が静かに通るか」をファイルヘッダに書くのは例ベースと同じ
- **例ベーステストは消さない** — 例は境界の代表例 (ドキュメント性)、プロパティは全入力の性質。`*.test.ts` (例) と `*.property.test.ts` (性質) を並置する
- **アルファベットを絞った arbitrary を作る** — `fc.constantFrom(...文字集合)` を unit にした `fc.string`。全 Unicode より shrink が効き、反例が読める。サロゲートペア (絵文字) は意図的に混ぜる (今回それが穴を見つけた)
- **ドメイン型の arbitrary は手書きする** (`fc.record`)。zod → arbitrary の自動導出ライブラリ (zod-fast-check 等) は zod のバージョン追従が重いので入れない。生成した Problem は不変条件 (mentionCount = mentions.length) を満たすよう `.map()` で整合させる
- **成り立たない性質は `it.fails` で固定する** — 「この性質は現状成り立たない」を機械記録にする。①勝手に直さない (振る舞い変更は裁定後)、②直したら it.fails が落ちて昇格を強制される、の両方が効く。コメントに未決の所在 (domain_rules.md の節) と昇格手順を書く
- **決定的な反例領域で it.fails を書く** — fc がたまたま反例を見つけない run があると it.fails 自体が落ちる。反例が必ず出る arbitrary (例: 日時範囲を分離する / 必ずペア境界を跨ぐ長さにする) に絞る

### 落とし穴 (今回踏んだもの)

- **往復性質は「正規化」に負ける** — split/join, parse/format 系は大抵どこかで trim・空白除去・重複除去をしており、厳密往復は成り立たない。「どの正規化を除いて成り立つか」まで書けて初めて仕様になる (それ自体に価値がある)
- **`.length` は文字数ではない** — UTF-16 コードユニット数。仕様の「N 文字」がユニットなのか、コードポイントなのか、書記素なのかを確かめること。fast-check の `unit: "grapheme"` は絵文字を 1 単位で生成するので、この差を自然に炙り出す
- **プロパティ内で外部の実装をコピーしない** — 期待値の再実装 (例: max の reduce) は「実装の写し鏡」化リスク。今回 withDerived の検証で使ったのは、性質の定義そのもの (最大 createdAt) だから許容。迷ったら「実装が変わってもこの式は仕様として残るか」で判断

## 4. フロントエンド (React) への適用可否 — 調査結論

対象レイヤ別に、この repo の実コード (`apps/frontend/src/`) を根拠に判断した。

### 4.1 純粋ロジック層 — ✅ 効く (適用済み)

BFF と完全に同じ書き味で使える。実証: `sessionTitle.property.test.ts` (上記 §1)。この層に該当する実ファイル:

- `consultation/sessionTitle.ts` (タイトル導出 — 適用済み)
- `voice/stitcher.ts` (認識結果の縫い合わせ。クラスだが React 非依存・時刻非依存)
- `voice/echoGate.ts` (エコー破棄の門。時刻を引数で受ける設計なので、時刻列を arbitrary にした性質が書ける — 例:「playing 中に届いた結果は時刻によらず必ず破棄」)
- `components/screens/problemShared.ts` の `relativeDays` (現在時刻に依存 — `Date.now` を注入できるようにすれば書ける)

frontend は #142/#135 のリファクタで「純粋ロジックはファイルに切り出して [L1]」の構造が既にでき上がっており、**BFF の domain/ と同じ入場条件 (静かに間違う導出・変換) をこの層に適用すればよい**。

### 4.2 hooks (useConsultation / useTextToSpeech / useVoiceInput) — ⚠️ 原理上は可能、現時点では入れない

fast-check の **model-based testing** (`fc.commands`) + `renderHook` で「操作列を生成して不変条件を検証する」ことは原理上できる。しかしこの repo の hooks は:

- 中身のほとんどが **api 呼び出しの結果反映と画面遷移** (useConsultation) や **ブラウザ API との格闘** (useTextToSpeech: HTMLAudioElement / SpeechSynthesis / fetch)。性質にすると「mock がこう返したらこう表示する」になり、**性質の形をした例テスト** (偽物の検証) に退化する
- 非同期 (await 列) + タイマーが絡み、fast-check の shrink が「再現しない反例」を出しやすい (実行順序が縮小で変わるため)
- 状態機械として面白い部分 (echoGate / stitcher) は**既に純粋クラスとして hooks の外に切り出されている**。= テスト可能性を設計基準にする方針 (strategy §1.4) が働いた結果、hooks 側にプロパティで守る価値のある純粋ロジックが残っていない

**結論: hooks に不変条件が必要になったら、まずロジックを純粋クラス/関数に切り出して §4.1 に落とす。** hook のままプロパティを書くのは設計の警報 (strategy §1.4) とみなす。

### 4.3 コンポーネント (model-based testing で UI を操作する) — ❌ 入れない

`fc.commands` で「クリック列を生成 → 画面状態の不変条件を検証」する手法は存在するが、この repo では:

- UI 仕様の真実は **MDX** (ADR 0005)、描画の破壊検知は**実環境 E2E** が持ち場 (mock E2E は廃止方針 / strategy.md §6.3)。プロパティで守るべき「静かに間違う導出」はコンポーネント層に置かない構造になっている (置いたらそれが警報)
- 1 操作 = render + イベントループで、数百ケース × shrink の実行コストが純粋関数の単体の比ではない。strategy §1.5 の実測 (中間層のモック E2E が一番よく壊れる) に照らすと、**維持費だけ増えて実績が出ない**中間層をもう 1 つ作ることになる

**結論: コンポーネント層には導入しない。** 将来、複雑な状態機械を UI が直接持つ画面 (例: ドラッグでの Mention 再リンク) が生まれたら、その状態機械を純粋関数に切り出して §4.1 で書く。

### 6.2 hypothesis の流儀 (fast-check 側との対応)

TS 側 (§3) と揃えたところ:

- **性質 1 つ = テスト関数 1 つ**。テスト名は `test_<英語の性質文>`、docstring の 1 行目を `[単体] <日本語の性質文>` にする (pytest は日本語関数名も動くが、既存 `cicd/scripts/` は英語名なので合わせた)
- **例ベーステストは消さない** — `test_check.py` / `test_persistent_layer_guard.py` は残し、`test_*_property.py` を**並置**する (TS の `*.test.ts` / `*.property.test.ts` と同じ関係)
- **入力ドメインを構成で絞る** — 「実装の判定式をテストにコピーして filter する」のではなく、**行頭の 1 文字を安全な集合から引く**などの**組み立て方**で不変条件を保証する (実装の写し鏡を作らないため)
- **seed は固定しない**。反例の再現は「反例を例ベーステストとして固定化する」で担保し、`.hypothesis/` (反例 DB) は commit しない (`.gitignore`)。commit すると「DB に入っているから緑」に依存でき、固定化の運用が骨抜きになる
- **反例が出たら、まず例ベースに固定してから直す**。実装が仕様より弱いと分かった場合は**直さずに** Issue を立て、性質を弱めた理由をコメントと PR に残す

Python 固有で決めたこと:

- **`settings(max_examples=200, deadline=None)` をファイル先頭の定数に置き、デコレータとして使い回す** (`@PROPERTY`)。`deadline` を切るのは、中身が純粋な文字列処理でありながら CI 共有ランナーの初回実行が既定 200ms を超えうるため — **落ちる理由を性質違反だけにする**
- **`max_examples` は既定 100 の倍 (200)**。実測コスト: `npm run test:scripts` が **35.8 秒 → 45.7 秒 (+9.9 秒 / 16 本)**。ここは「包み方 × 入れ子 × 他の全引数」の組み合わせで効く場所なので探索は厚くしたいが、この +10 秒が上限の目安 (これ以上必要になったら `max_examples` を上げる前に、性質を分割して対象を絞る)
- **生成器そのものの健全性を例で固定する** — プロパティは「生成器が意図した入力を作れている」ことに全面的に乗るので、生成器が静かに壊れると性質は緑のまま**何も検証しない**。`test_plain_lines_never_contain_a_sha_token` はその 1 行の保険

### 6.4 分かったこと (Python 側の落とし穴)

- **入口 (公開関数) を主語にした性質は、二重防御に守られて空振りする。** 最初は
  `has_pm_accept` / `has_standin_review` を主語に「包みの中の宣言は門を開けない」と書いたが、
  この 2 つは**マーカーを桁 0 に限る**別の防御も持っているため、引用・インデントの除外を
  丸ごと壊しても緑のままだった (上表の 🟢 2 件)。**二重防御のどちらか一方が静かに死ぬ**のを
  防ぐには、`_machine_lines` 自身の契約 (「包みだけの本文からは機械行が 1 行も出ない」) を
  別の性質として直接置く必要がある。→ 「入口で言えるから十分」ではなく、
  **壊したい 1 行ごとに、それを主語にした性質があるか**で見る
- **冪等・往復は join/splitlines の正規化に負ける (TS 側 §3 の落とし穴と同型)。**
  `_machine_lines(join(once)) == once` は空行だけの本文で落ちる — `"\n".join([""])` は `""` で
  `"".splitlines()` は `[]`。性質ではなく往復側の都合なので、右辺も同じ往復を通した
  「不動点」の形 (`_machine_lines(joined) == joined.splitlines()`) に言い換えた
- **平文の生成器が「うっかり当たり」を作らないよう文字集合を削る。** 地の文の生成に
  `a-f` / `3-8` を混ぜると、包みの外の無意味な文字列が偶然 SHA トークンになって
  「性質ではなく生成器の事故」でテストが落ちる。**hex を作れない文字だけで地の文を作る**
- **`decide` のような多引数の判定は、守りたい 1 点を残して全引数を `@given` に流し込むのが効く。**
  「逃げ道が無い」は他の全引数を渡り歩いて初めて言えることで、例をいくつ並べても
  「その組み合わせは試していない」が残る (層ガードの `test_default_management_rg_is_never_deletable`)
