## 1. 芯 — 一行で

> **自分の雑な思考が投げ込まれたら、なんか構造化してくれて自分の人生の価値にしてくれたら良いんだよな** (PO / 2026-08-22 昼)

**投げ込む → 構造化される → 人生の価値になる。**

| 段           | 中身                                                        | 実装状態                                                      |
| ------------ | ----------------------------------------------------------- | ------------------------------------------------------------- |
| ① 投げ込む   | 雑なまま、整えずに出す — **加えて、生活の痕跡から取材する** | **半分** — 音声は「つぼ」(§5) だが、受動的取材は未着手 (§1.2) |
| ② 構造化     | 機械が仮説を言語化し、本人は ○× を押すだけ (§1.3)           | **半分** — かつ**それ自体は価値ではなかった** (§3.3)          |
| ③ 価値になる | 「私を深く知っている状態」があらゆる応答に効く              | **未開拓** — 最有力候補が出た (§1.1)                          |

③ が空いていることが、v1 → v2 の最大の差分。**ただし深夜の長考で、③ に名前が付いた。**

### 1.1 ③ の最有力候補 — ライフ IQ / プライベート IQ

> **いわゆるワーク IQ 的なもの? ワークじゃないんだけど、私のライフ IQ というかプライベート IQ 的なものが実装されるといい** (PO / 2026-08-22 深夜)

仕事文脈を全部知っていて効くアシスタント基盤 (Work IQ) の**私生活版**。

**反転がここにある**:

| これまでの読み方              | ライフ IQ の読み方                                     |
| ----------------------------- | ------------------------------------------------------ |
| 蓄積は**見る**もの (成果物)   | 蓄積は**効く**もの (裏方・燃料)                        |
| 価値 = 画面に出てくるレポート | 価値 = **私を深く知っている状態**そのもの              |
| 「構造化されたものを読む」    | 「構造化されているから、返ってくるものが的を射ている」 |

- **効き先は全部**: 日中の応答、深掘り質問の当たり、夜勤が何を選ぶか、提案の解像度 — 全部がライフ IQ の高さに依存する
- **だから構造化は捨てない。読ませるのをやめる** — §3.3 と §5 の本音 (「構造化画面はあんまり見ない」) と矛盾しないのはこの読み方だけ
- **差別化の線もここから引ける** → §6

### 1.2 ライフ IQ をどう作るか — 取材論

> **どうやってライフ IQ を作るか。それはもう日常の行動の中にないといけないんだよね。要は、アプリに投げかけた時の情報だけでやるのはもう無理だと思う** (PO / 2026-08-22 深夜)

**能動的な吐き出し (音声) だけでは、取材として不足する。** 人生は、本人が説明しない場所に痕跡を残すから。

これは音声の格下げではなく、**音声が本命ではなく代替チャネルだった**という発見。「身体情報も全部投げたいけど無理だから自分で説明している」という以前の言葉と同じ糸で繋がっている。

| 取材のしかた         | 中身                                                          | 席はあるか                                                                                                              |
| -------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **能動的な吐き出し** | 本人が話す・書く (音声キャプチャ)                             | 済 — ただし「これだけでは無理」                                                                                         |
| **受動的取材**       | 生活が既に痕跡を残す場所から agent が**読みに行く**           | **M3 の「外部データ read-only ツール」がまさにこの席** (ADR 0015 / #84)。骨組みは計画済みで、**何を繋ぐかが未定だった** |
| **接点の反転**       | 目的地アプリに来てもらうのではなく、生活の側に agent が出向く | プッシュ / 朝のダイジェスト (M3-3)                                                                                      |

#### どこから取材するか — PO の価値順 (2026-08-22 深夜、選択済み)

「Life IQ に一番効くソースはどれか (価値の大きさ)」への選択:

| 候補                                                                                        | 選ばれたか                                            |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **メール・メッセージ** (人間関係・仕事の文脈)                                               | ✅                                                    |
| **行動ログ** (位置・スクリーンタイム・購買等 —「言ってること」と「やってること」のギャップ) | ✅                                                    |
| カレンダー・予定                                                                            | ❌                                                    |
| 身体・健康データ                                                                            | ❌ (以前「投げたい」と挙がったが、価値順では選ばれず) |

**読み方**:

1. **Life IQ の価値核 = 「誰とどうやりとりし、実際に何をしているか」** — 自己申告 (音声) やバイタルより、**コミュニケーションと実行動が本人を語る**という選好
2. **選ばれた 2 つはプライバシー要求が最高域** → **セキュリティ構造は衛生要件ではなく、プロダクト価値のクリティカルパス**になった。「**機微データを預けても大丈夫な構造**」自体が差別化要素
3. **これは「価値の順」であって着手順ではない** — 技術的に近く低リスクなもの (カレンダー等) から始めて信頼を作る、という進め方はあり得る (→ **裁-21**)

#### 直列の前提 — #319

**受動的取材は #319 (会話セッションに所有者の次元が無い) の解消を直列の前提にする。** 他人のデータが混入しうる構造のまま、外部データを吸うことはできない。外部への **write** は引き続き個別再ゲート (ADR 0015)。

つまり **#319 は「セキュリティの宿題」ではなく「ライフ IQ の前工程」**。ここが v2 で最も強く結線される依存。

### 1.3 表出化ループ — 言語化の仕事を、本人から機械へ移す

> **暗黙知というのかな。言語化されてない情報も含めて取り扱いたい。でも今の板ベースは言語化しないと駄目で、そのコストが高い。どうしたらいいんだろうね** (PO / 2026-08-22 深夜)

**提案 (窓口 PM / PO 未裁定): 構造に暗黙知を入れようとしない。言語化する人を替える。**

```text
受動的取材 (言語化を要求しない: メール・行動ログ・垂れ流し音声)
  → 夜勤が「あなたはこうかもしれない」という仮説を言語化 (表出化)
  → 気づきカードで本人が ○×  (生成は高コスト、判定は低コスト)
  → 頷かれた仮説だけが形式知として蓄積に入る
```

**このループが「ライフ IQ をどう作るか」の答えの本体**。§1.2 が入口 (何を取材するか) なら、ここは製法 (取材したものをどう知識に変えるか)。

**それぞれの再定義**:

| 部品             | これまでの理解                | 表出化ループでの仕事                                                                                                                    |
| ---------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **気づきカード** | 気づきを通知するもの (M3-3)   | **暗黙知の仮説を ○× で確定させる装置**。通知 UI ではなく、知識生成の心臓部                                                              |
| **音声**         | 言語化して入力する手段        | **言語化コストが最も低い漏出チャネル** — きれいに話さなくてよい。将来のリアルタイム音声では声色・間などの非言語信号も取材対象になりうる |
| **本人の仕事**   | 話す・書く・整理する          | **○× を押すだけ** (生成せず、判定する)                                                                                                  |
| **構造化**       | 本人の思考を figures に起こす | 仮説を**判定可能な形**に整えること (§3.3 の「手段」の中身がこれ)                                                                        |

**この方式は既に実証されている** — このコンセプト対話そのものがループの実例。PO は構造を一度も書かず、雑に発話しただけ。窓口 PM が言語化・構造化し、○× 確認で Issue #266 に形式知が積み上がった。「**PM 体験の Mind Inbox 版**」(§3) の中身は、まさにこのループ。

**製品仕様の一行候補** (→ **裁-23**):

> ### 「あなたは言語化しなくていい」

**⚠️ §3 の「受信箱は脇役」(裁-3) との関係**: 搬送路としての**受信箱・通知**は脇役のままでよいが、**気づきカードの中身 (○× で確定させる仕事) は脇役ではない**。両者を分けて扱う必要がある — 裁-3 に ○ を付ける場合も、この区別は残る。

**○× をください**

- **裁-1**: この 3 段を v2 の骨格にする → **○ / ×**
- **裁-14**: **「ライフ IQ / プライベート IQ」を ③ の答え = v2 の核概念に据える** → **○ / ×**
  - × のときは、「これは違う」とだけ書いてもらえれば十分 (代案は次の対話で)
- **裁-19**: **受動的取材 (生活痕跡の read-only 取り込み) を、ライフ IQ の必須構成要素として v2 に書く** → **○ / ×**
  - ○ なら、音声は「唯一の入口」ではなく「取材チャネルの 1 つ」として書き直される
- **裁-20**: **「機微データを預けても大丈夫な構造」自体を差別化要素として v2 に明記する** (#319 / E2E 方針をコンセプトの一部にする) → **○ / ×**
- **裁-22**: **表出化ループ (取材 → 仮説の言語化 → ○× → 形式知) を、ライフ IQ の作り方の中核メカニズムとして v2 に据える** → **○ / ×**
  - ○ なら、気づきカード (M3-3) は「通知 UI」から「知識生成の心臓部」に格上がる
- **裁-23**: 製品仕様の一行として **「あなたは言語化しなくていい」** を掲げる → **○ / ×**
  - 5 秒で決まる。× なら、代わりに掲げたい一行があれば書いてほしい

## 3. 核は 3 点セット — 夜勤 / 記憶 / 構造化

2026-08-22 昼の対話で PO が選んだのはこの 3 つ。**受信箱・通知は選ばれなかった** (脇役)。

出典: 「今 Fable にやってもらっているのはかなり助かるんだよね。**これの Mind Inbox 版がいいよなー**」(PO / 2026-08-22 昼)

つまり **参照モデルは、この開発で実際に回っている hub-and-spoke の PM 体験そのもの**。Mind Inbox は「**内面プロジェクトの窓口 PM**」になる。

### 3.1 夜勤 — 寝てる間に進んでる

> **私が稼働してないうちに私の人生を進めて欲しいんだよな** (PO / 2026-08-22 昼)

- 作業対象は**タスクではなく人生**。未読を減らすのでも TODO を消化するのでもない
- 朝、成果と要約が待っている
- 対応する実装: M3-2 内部整理 (棚卸し・再グルーピング・ダイジェスト) + M3-4 深掘り
- **自律の範囲は可逆な操作だけ** (ADR 0015 G3)。不可逆・外部への作用は承認を取る → §8
- **競合が張っていない線**でもある (ChatGPT は呼んだときだけ動く) → §6

### 3.2 記憶 — 覚えていて即答

- 「あれなんだっけ」に文脈込みで即答する。**自分で記憶も管理もしない**
- 対応する実装: M2 ナレッジ層 (embedding 索引 + RAG / #83)
- **M2 は技術タスクではなく「記憶」という体験の実装**。M2 → M3 の順序はこの核と整合する
- **ライフ IQ の実体はここ** — 「私を深く知っている状態」は、索引された蓄積そのもの (§1.1)
- **RAG の使い道が決まった**: 一般論の解決アイディアではなく「**過去の自分の決め方・効いた対処**を引く」(§6)

### 3.3 構造化 — 曖昧でも構造化される / ただし「見ない」

**ここに緊張がある。隠さずに書く。**

| いつ            | PO の言葉                                                    |
| --------------- | ------------------------------------------------------------ |
| 2026-08-22 昼   | 「**曖昧でも構造化される**」を核の 1 つとして選択 ✅         |
| 2026-08-22 深夜 | 「構造化の画面は**あんまり見ないし、見てもよく分からない**」 |

**矛盾ではない、という読み方 (窓口 PM の解釈 / PO 未裁定)**:

- 昼に選ばれたのは「**構造化される**」という**状態**であって、「構造化を**見る**」という体験ではなかった
- つまり **構造化は目的ではなく手段** — 出力先は画面ではなく、**ライフ IQ という裏方** (§1.1)
- 「ふわっと言うだけで整理される」ことの価値は、**次にものを言ったときに返ってくるものが的を射ている**ことで回収される

**この解釈を採ると何が変わるか**:

- 構造化の**精度**への投資は続く (ライフ IQ の燃料なので)
- 構造化の**見た目**への投資は下がる (読まれないので)
- **#187 (2 ペイン化) の優先度に再考の余地が出る** — 「構造が見える」を主役に据える設計は、この本音と衝突しうる → **裁-16**

なお実装面では、**人が直した差分そのものが濃い素材**という 2026-08-11 の裁定 (「良い」) は生きている。見せる理由は「読ませるため」ではなく「**直させるため**」に絞れる。

**§1.3 の表出化ループと繋がる**: 「直させる」の最小形が気づきカードの ○×。構造化の仕事は「本人の思考を図に起こすこと」ではなく「**仮説を判定可能な形に整えること**」。

### 3.4 参照モデルの対応表

## 6. 競合 — ChatGPT (+ Notion 連携) に対してどこに線を引くか

> 汎用対話は向こうが強く、構造化も Notion 連携で埋まりつつある。**そこのインセンティブがない** (PO / 2026-08-22 深夜)

**汎用チャット・汎用構造化では勝てない。** これは v2 の前提として書く。張れる線は 4 本:

| 線       | ChatGPT 側             | Mind Inbox が張るべき側                                                              | 実装状態                                                                |
| -------- | ---------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| **入力** | テキスト中心           | **摩擦ゼロの音声キャプチャ** + **生活痕跡からの受動的取材** (§1.2)                   | 音声はつぼだが弱い (#120 / #121) / 受動的取材は未着手 (#84 / #319 待ち) |
| **文脈** | セッション的・汎用     | **縦断的な私秘コンテキスト** (何か月にもわたる自分の履歴)                            | 🔁 繰り返し検出で実証済み                                               |
| **出力** | 一般論の解決アイディア | **自分知識から引く提案** — 過去の自分の決め方・効いた対処。**M2 RAG の使い道はこれ** | 未実装 (M2 / #83)                                                       |
| **稼働** | 呼んだときだけ         | **夜勤** — 稼働していないうちに人生を進める                                          | 未実装 (M3)                                                             |

**4 本とも「私秘性」と「時間」に依存している** — 汎用モデルが原理的に持てないもの (その人の縦の履歴) だけを資源にしている。これが §1.1 のライフ IQ と同じことを競合の言葉で言い直したもの。

**5 本目になりうる線 — 預けられること**: 受動的取材で選ばれた 2 つ (メール・メッセージ / 行動ログ) は**プライバシー要求が最高域** (§1.2)。つまり「**機微データを預けても大丈夫な構造**」を作れること自体が、汎用チャットが簡単には越えられない線になる。**セキュリティ構造 (#319 / E2E 方針) は衛生要件ではなく価値のクリティカルパス** → **裁-20**。

**注意**: 「Notion 連携で構造化が埋まりつつある」は、構造化**機能**での差別化が閉じつつあるという意味。§3.3 の「構造化は手段」という読みと同じ方向を指している。

  - 根拠: 「人間の思考の中心は Problem。『シンキング』だと曖昧すぎる」(PO / 2026-08-11)
  - 補強 (rev.2): ライフ IQ は**入力の幅が広いほど濃くなる**ので、入口を絞らない方が整合する
- **案 B**: Problem 以外の受け皿 (アイデア / 願望) を 2 層モデルに足す
  - 影響: ADR 0007 の改訂が要る

**→ A に ○ / B に ○**

### 裁-10. 音声対話の位置づけ (rev.2 で材料が増えた)

**新しい材料**: 音声で楽に投げ込むのは「**つぼ**」(実証済みの ○ 2 つのうち 1 つ)。ただし体験は弱く (#121 途切れ / 認識精度)、**リアルタイム性が無い** (#120)。

**さらに深夜の取材論で前提が動いた**: 「アプリに投げかけた時の情報だけでやるのはもう無理」= **音声は本命ではなく代替チャネル**だった (§1.2)。主軸の座を争う相手が「夜勤・記憶・構造化」だけでなく**受動的取材**にも増えた。

**ただし表出化ループ (§1.3) では役割が復活する** — 音声は「言語化して入力する手段」ではなく「**言語化コストが最も低い漏出チャネル**」。きれいに話さなくてよいので、暗黙知が漏れ出す入口として代えが利かない。リアルタイム化 (#120) は、声色・間などの**非言語信号まで取材対象にする**という意味を持ちうる。

- **案 A**: **投げ込み口の 1 つに格下げ**。「低負荷であること」は残すが、主軸の座は「夜勤・記憶・構造化」に譲る (rev.1 の推奨)
- **案 B (rev.2 で有力化)**: **主インターフェースとして維持し、投資する** — §6 の「入力」の線がこれ。実証済みの ○ を伸ばすのが最短 (#120 / #121 を優先度上げ)
- **案 C**: 位置づけは A (脇) のまま、**#121 (体験の弱さ) だけ直す**。#120 (リアルタイム化) は保留
- **案 D (rev.3 の推奨)**: **「漏出チャネル」として位置づけ直す** — 主軸/脇の議論から降ろす。要件が変わる: #121 の目標は「正確な書き起こし」ではなく「**意図の取りこぼしを減らす**」、#120 は「速い応答」ではなく「**非言語信号まで取材する**」

**→ A / B / C / D のどれかに ○**

### 裁-11. KPI の組み替え

v1 §12 の 5 指標のうち「**採用率 (Next Step) — 行動や相談に接続できているか**」は、「解決率を成功指標にしない」と緊張する。

- **案 A (推奨)**: 採用率を外し、「**夜勤の成果への反応率**」(届いた気づき・整理に本人が触ったか) に置き換える
- **案 B**: 5 指標は維持し、解釈だけ「未解決 = 失敗ではない」と注記する
- **案 C (rev.2 で追加)**: 裁-15 が ○ なら、**「構造化画面の再訪率」を KPI から外す** (見ないものを測っても意味がない)。代わりに「応答が自分の履歴から引かれていたか」を測る

**→ A / B / C のどれかに ○** (C は A と併用可)

### 裁-12. 外からの輸入 (ChatGPT / Claude Code の思考ダンプ)

- **案 A (推奨)**: v2 では「①投げ込む」の拡張として 1 節だけ置く (コア動線にはしない)
  - 形: 生ログ接続ではなく、既存の 2 段処理 (Dump → Mention 抽出 → グルーピング) を**濾過装置としてバッチ輸入**。opt-in・トリアージで可逆 (G3 整合)
- **案 B**: v2 のコア動線に格上げする
  - 補強 (rev.2): 「ChatGPT に流れる」(§5) なら、**流れた先の思考を回収できること自体が防衛線**になる。ライフ IQ の濃さは投入量に比例する

**→ A に ○ / B に ○**

### 裁-13. マルチエージェント (人格分離) をコンセプトに書くか

- **案 A (推奨)**: **体験の言葉としてだけ書く** — 「前面は共感に専念し、裏方が解剖する」。技術選定 (Magentic 型) は ADR 0016 のまま M3 で再評価
- **案 B**: 技術構成としても v2 に明記する
  - 補足: PO はマルチエージェンティック / Magentic 志向を明言済み (2026-08-11)。ただし ADR 0016 は「research preview 級は仕様変動リスクがあるため M3 まで採用遅延」

**→ A に ○ / B に ○**

### 裁-16. 2 ペイン化 (#187) の位置づけ (rev.2 で新設)

深夜の本音「構造化の画面はあんまり見ないし、見てもよく分からない」が直撃する論点。

- **案 A**: **予定どおり主役に据える** — 「単なるチャットは嫌」への回答は「構造が見えること」だという読み。見て分からないのは**今の見せ方が悪いから**であって、構造化を見せること自体は正しい
- **案 B (rev.2 の推奨)**: **裏方の点検窓に格下げ** — 主役はライフ IQ の効き (応答の的中)。構造化画面は「**直させるため**」に残すが、体験の中心には置かない。#187 の優先度を下げ、その分を §6 の 4 本の線に回す
- **案 C**: 判断を保留し、**#187 を小さく作って反応を見る** (見せ方を変えれば「分かる」になるのかを実測してから決める)

**→ A / B / C のどれかに ○**

### 裁-17. 解決提案は「自分知識ベース」に限るか (rev.2 で新設)

「解決アイディアも一般論で**まあそうなんだけどな**」(PO / 深夜) への対応。

- **案 A (推奨)**: **自分知識から引くものに限る** — 「前に似た状況で、あなたはこう決めて、こう効いた」。引ける履歴が無いときは**提案しない** (黙る)
  - 理由: §6 の「出力」の線そのもの。一般論は ChatGPT に勝てない
  - 副作用: 使い始めは提案がほぼ出ない (蓄積が薄いため)
- **案 B**: 一般論も出すが、**自分知識由来のものを明示的に区別して見せる** (「あなたの履歴から」バッジ)
- **案 C**: 現状維持 (一般論も普通に出す)

**→ A / B / C のどれかに ○**

### 裁-21. 受動的取材をどこから繋ぐか (着手順)

**価値順は決着済み** (メール・メッセージ / 行動ログ = ✅、カレンダー / 健康 = ❌)。残るのは**着手順** — PO 自身が「価値順 ≠ 着手順」と留保している。

- **案 A**: **価値順どおり、メール・メッセージから**。一番効くものを最初に取りに行く
  - リスク: プライバシー要求が最高域のものを、実績ゼロの状態で預けてもらうことになる
- **案 B (推奨)**: **技術的に近く低リスクなもの (カレンダー等) で先に信頼と配管を作り**、その後で価値順の 2 つへ
  - 理由: PO 自身が挙げた進め方。read-only ツール接続の骨組み (#84) の検証を、失っても痛くないデータで済ませられる
  - コスト: 価値の実感が後ろにずれる (カレンダーは価値順で ❌ だったので、これ自体では刺さらない)
- **案 C**: **#319 が終わるまで着手順を決めない** (前提が片付いてから改めて裁定)

**→ A / B / C のどれかに ○**

<small>どの案でも **#319 (所有者次元) の解消が直列の前提**であることは変わらない (§1.2)。</small>

### 特に効くのはこの 3 つ

急ぐなら、ここだけでも。**rev.2 で入れ替えた。**

- **裁-14** (ライフ IQ を核概念に据えるか) — ③ の答えそのもの。ここが決まれば §6 の線が投資計画になる
- **裁-19** (受動的取材を必須構成要素にするか) — ○ なら **#319 が最優先の前工程に格上がりし、ロードマップの形が変わる**
- **裁-16** (2 ペイン #187 の位置づけ) — 「構造化画面を見ない」という本音を設計に反映するかどうか。**実装の優先度が今すぐ動く**

**5 秒で決まるので、ついでにこの 2 つも**: **裁-23** (一行「あなたは言語化しなくていい」を掲げるか) と **裁-8** (v2 は書き直しか追補か — これが無いと執筆が始まらない)。

<small>rev.1 で挙げていた 裁-5 (価値化の定義) と 裁-9 (脳内全部か) は、深夜コメントで**前提が動いた / ほぼ決着した**ため 3 位以内から外した。すべて §10 に残っている。</small>
