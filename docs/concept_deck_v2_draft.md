## 3. 核は 3 点セット — 夜勤 / 記憶 / 構造化

2026-08-22 の対話で PO が選んだのはこの 3 つ。**受信箱・通知は選ばれなかった** (脇役)。

出典: 「今 Fable にやってもらっているのはかなり助かるんだよね。**これの Mind Inbox 版がいいよなー**」(PO / 2026-08-22)

つまり **参照モデルは、この開発で実際に回っている hub-and-spoke の PM 体験そのもの**。Mind Inbox は「**内面プロジェクトの窓口 PM**」になる。

### 3.1 夜勤 — 寝てる間に進んでる

> **私が稼働してないうちに私の人生を進めて欲しいんだよな** (PO / 2026-08-22)

- 作業対象は**タスクではなく人生**。未読を減らすのでも TODO を消化するのでもない
- 朝、成果と要約が待っている
- 対応する実装: M3-2 内部整理 (棚卸し・再グルーピング・ダイジェスト) + M3-4 深掘り
- **自律の範囲は可逆な操作だけ** (ADR 0015 G3)。不可逆・外部への作用は承認を取る → §6

### 3.2 記憶 — 覚えていて即答

- 「あれなんだっけ」に文脈込みで即答する。**自分で記憶も管理もしない**
- 対応する実装: M2 ナレッジ層 (embedding 索引 + RAG / #83)
- **M2 は技術タスクではなく「記憶」という体験の実装**。M2 → M3 の順序はこの核と整合する

### 3.3 構造化 — 曖昧でも構造化される

- ふわっと言うだけで、過去の文脈と突き合わせて整理・言語化される
- 対応する実装: Mention 抽出 → グルーピング (ADR 0007) の自律化
- **人が直した差分そのものが自己理解データ** (2026-08-11「良い」裁定) — AI の整理と本人の感覚のズレが、いちばん濃い素材

### 3.4 参照モデルの対応表

| PM 体験                        | Mind Inbox 版                        | 実装                 |
| ------------------------------ | ------------------------------------ | -------------------- |
| 寝てる間に作業が進んでいる     | 夜勤 (内部整理・深掘り)              | M3-2 / M3-4          |
| 「あれどうなってたっけ」に即答 | 記憶 (蓄積への RAG)                  | M2 / #83             |
| 雑に言うと整理されて返ってくる | 構造化 (Mention → Problem)           | 実装済 + M3 で自律化 |
| 朝、要約と裁定 3 件が届く      | 受信箱 + 気づきカード / ダイジェスト | M3-3 (**脇役**)      |
| 不可逆なことは必ず聞かれる     | HITL 承認                            | ADR 0015 G1          |

**○× をください**

- **裁-2**: 「内面プロジェクトの窓口 PM」を v2 の中心メタファーにする → **○ / ×**
- **裁-3**: 受信箱・通知は**主役ではなく搬送路**として扱う (磨き込みの優先度を下げる) → **○ / ×**

## 4. 何でないか

> **単なるチャットは嫌なんだよね。** (PO / 2026-08-22)

| ✗ これではない                   | なぜ違うか                                                                                                                                                               |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **チャットボット**               | チャットは投げ込み口にすぎない。主役は会話の外に積み上がる構造 (Problem 層) と価値。**会話は忘れてよい** (実装もそうなっている — 会話履歴は窓で落ち、覚える場所は蓄積層) |
| **メモ / 日記アプリ**            | 整理・構造化・深掘りを人間が担うなら v1 の課題に戻る                                                                                                                     |
| **TODO / タスク管理**            | 夜勤の目的語は人生であってタスクではない。未読 0 も完了率も目標ではない                                                                                                  |
| **問題解決ツール**               | 「**解決しない Problem の方が多い**」(PO / 2026-08-11)。解決率を成功指標にしない                                                                                         |
| **診断・治療**                   | v1 から不変。自己理解・整理・相談準備の支援                                                                                                                              |
| **記録さえ残ればよいログ**       | 構造化されない蓄積は v1 §11 Gap 2 そのもの                                                                                                                               |
| **外部に資産を切り売りする基盤** | MCP サーバー化 (外への公開) は保留。方向は逆で「**外で考えたことの輸入**」(2026-08-11)                                                                                   |

**設計への直結**: UI の主役を会話から構造物へ移す = **2 ペイン化 (#187) は「単なるチャットは嫌」への直接回答**。

**○× をください**

- **裁-4**: この「何でないか」7 行をそのまま v2 に載せる → **○ / ×** (× なら、消したい行に印を)

## 5. 4 動詞 — ツール = 資産の運用装置

Issue #266 論点 2。蓄積を「資産」と見たときの運用動詞。

| 動詞         | 意味                                 | 状態       | PM の動詞での言い方 |
| ------------ | ------------------------------------ | ---------- | ------------------- |
| **貯める**   | 投げ込みが Mention として残る        | 済         | 起票する            |
| **引き出す** | 必要なときに文脈込みで出てくる       | M2 (#83)   | 「あれ」に即答する  |
| **検証する** | 仮説の履歴・早期サインを突き合わせる | **未開拓** | 調べておく          |
| **換金する** | 再言語化コストを払わずに価値へ変える | **未開拓** | 報告する            |

- **未開拓の 2 つ (検証・換金) が §1 の③ そのもの**
- ツール題材の刷新 (#321) は、この 4 動詞から逆算して完了条件が書ける (現状は SK 時代の受信箱デモのまま: `search_faq` / `get_inbox_stats` / `send_reply` / `archive_message`)

### 5.1 「価値化」をどう定義するか (窓口 PM の提案 / PO 未裁定)

抽象で決めない。**最初の「価値」の実物への反応で定義する**:

1. PO が dev 環境に実データを投げ込む (ドッグフーディング)
2. 蓄積から傾向レポートを 1 枚生成する (#244 自己理解レポート)
3. 「これは価値だ / 違う」という反応が、そのまま「換金する」の定義になる

**○× をください**

- **裁-5**: 「価値化」は抽象で先に決めず、**#244 レポート試作への反応で定義する** → **○ / ×**
- **裁-6**: 4 動詞 (貯める / 引き出す / 検証する / 換金する) を v2 の章立てに入れる → **○ / ×**

## 6. 開発体制との写像 — 委任境界をそのままプロダクトに敷く

この開発で回っている hub-and-spoke の委任境界 ([`docs/team.md`](team.md)) と、ADR 0015 のガードレールは**同じ形をしている**。2026-08-22 の対話で共有した符合を、v2 では明示的な設計原則として据える案。

| 開発体制 (team.md)                           | プロダクト (ADR 0015)                                                                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **① 聞かずに決めて事後報告** (可逆な判断)    | **内部整理は可逆に** (G3) — 再グルーピング・棚卸しは全部トリアージで取り消せる。やったことは受信箱に残る |
| **② PO に上げる** (不可逆・高コスト・北極星) | **副作用は HITL 承認** (G1) — 外部送信・通知・非可逆なデータ変更                                         |
| **③ 即時に聞く** (取り返しがつかない恐れ)    | 同上。**可逆かどうか自体が判定できないときは承認側へ倒す**                                               |
| 事後報告は「何を・なぜ」を残す               | **プッシュで届き、受信箱に残る** (G2) — 頻度予算・静穏時間・カテゴリ別オンオフはユーザー設定             |
| PO を待たせない (②で止まるのはその部分だけ)  | 承認待ちが夜勤全体を止めない                                                                             |

**含意**: 「なんかやっといてくれる」(外部への作用) は②の領域。だから**先に具体場面を決める必要がある** — 決まっていないものを自律させることはできない。

**○× をください**

- **裁-7**: 「可逆 = 自律 + 事後報告 / 不可逆 = 承認」を**プロダクトの明示原則**として v2 に書く → **○ / ×**

## 8. 未裁定の論点 — 裁定案の一覧

**ここが本体**。○ か × を付けてくれれば、次が動く。× のときは対案側に ○ を。

### 裁-8. v2 の形 — 書き直しか、追補か

Issue #266 論点 3。

- **案 A (推奨)**: v1 を置き換える **v2 として書き直す**。v1 は履歴として残す
  - 理由: 差分が骨格 (3 段モデル・夜勤・何でないか) に及ぶので、追補だと本文と矛盾する箇所 (§3「AI はまず受け止める」/ §4 プロアクティブ抑制) が読み手を誤らせる
- **案 B**: v1 はそのまま、**追補ページを足す**
  - 理由: 市場性・競争環境 (§9〜§11) は生きているので作り直しは無駄

**→ A に ○ / B に ○**

### 裁-9. 対象の広がり — 悩みだけか、脳内全部か

Issue #266 論点 1 (2026-08-11 でほぼ決着済みだが、正式裁定は未)。

- **案 A (推奨)**: **入口は脳内全部、モデルは Problem 中心のまま**。アイデアも願望も「Problem の素材」として飲み込む (受け皿を増やさない)
  - 根拠: 「人間の思考の中心は Problem。『シンキング』だと曖昧すぎる」(PO / 2026-08-11)
- **案 B**: Problem 以外の受け皿 (アイデア / 願望) を 2 層モデルに足す
  - 影響: ADR 0007 の改訂が要る

**→ A に ○ / B に ○**

### 裁-10. 音声対話の位置づけ

- **案 A (推奨)**: **投げ込み口の 1 つに格下げ**。「低負荷であること」という要件は残すが、主軸の座は「夜勤・記憶・構造化」に譲る
  - 根拠: 2026-08-22 の核 3 点に音声が出てこない。①投げ込むは手段を問わない
- **案 B**: v1 のまま**主インターフェースとして維持**
  - 根拠: 「心をすり減らさない」は v1 の中核価値で、そこは声の設計に依存する

**→ A に ○ / B に ○**

### 裁-11. KPI の組み替え

v1 §12 の 5 指標のうち「**採用率 (Next Step) — 行動や相談に接続できているか**」は、「解決率を成功指標にしない」と緊張する。

- **案 A (推奨)**: 採用率を外し、「**夜勤の成果への反応率**」(届いた気づき・整理に本人が触ったか) に置き換える
- **案 B**: 5 指標は維持し、解釈だけ「未解決 = 失敗ではない」と注記する

**→ A に ○ / B に ○**

### 裁-12. 外からの輸入 (ChatGPT / Claude Code の思考ダンプ)

- **案 A (推奨)**: v2 では「①投げ込む」の拡張として 1 節だけ置く (コア動線にはしない)
  - 形: 生ログ接続ではなく、既存の 2 段処理 (Dump → Mention 抽出 → グルーピング) を**濾過装置としてバッチ輸入**。opt-in・トリアージで可逆 (G3 整合)
- **案 B**: v2 のコア動線に格上げする (PO の実データが最も多く眠っている場所なので)

**→ A に ○ / B に ○**

### 裁-13. マルチエージェント (人格分離) をコンセプトに書くか

- **案 A (推奨)**: **体験の言葉としてだけ書く** — 「前面は共感に専念し、裏方が解剖する」。技術選定 (Magentic 型) は ADR 0016 のまま M3 で再評価
- **案 B**: 技術構成としても v2 に明記する
  - 補足: PO はマルチエージェンティック / Magentic 志向を明言済み (2026-08-11)。ただし ADR 0016 は「research preview 級は仕様変動リスクがあるため M3 まで採用遅延」

**→ A に ○ / B に ○**
