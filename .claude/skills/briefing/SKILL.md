# briefing (報告会)

節目の成果を **音声ナレーション付きスライド + 対話質疑** で PO に説明するリリース報告会モード。`debrief` が「PO が理解と承認を pull する」場なのに対し、`briefing` は **説明責任をエージェント側が負う** — PO は聞いて、引っかかったら突っ込むだけでよい。設計背景: Issue #116 (PO の理解がループ速度に追いつかない / 認知負債)、[ADR 0014](../../../docs/adr/0014-design-comprehension-gate-and-debrief.md) の系譜。形式の決定は Issue #116 の 2026-08-08 コメント (PO 決定: 音声ナレーション付き / 動画化しない)。

## いつ起動するか

- user が「報告会やろう」「リリース報告して」「/briefing」等と言ったとき
- リリース級のマイルストーン (epic 完了・機能バッチ着地・release-gate 通過) のとき、エージェントから提案してよい
- 日常の細かいマージは対象外 (それは `/status` と debrief)

## 設計思想

- **読む負担を PO からエージェントへ移す** — 「資料を作ったので読んでください」は禁止。エージェントが説明し切る
- **聞き流せる、しかし一方通行にしない** — 音声で耳から入れられるようにする。ただし動画 (完成録画) にはしない。割り込み質疑が報告会の核心
- **真実はライブ生成** — スライド内容は毎回 GitHub (マージ PR / Issue) と docs (ADR / MDX) から生成する。skill に内容をハードコードしない
- **30 分の器** — スライド 8〜10 枚 + 質疑。それを超える場合はスコープを絞るか 2 回に分ける

## 手順

### Step 1 — スコープ確定

`docs/debrief/journal.md` の直近の報告会 / debrief エントリをマーカーに、それ以降のマージ PR・完了 Issue・承認待ち事項 (Proposed ADR / rubric 初版等) を集める。「この回で PO が判断すべきこと」を先に列挙する (承認事項ゼロの報告会は情報量を疑う)。

### Step 2 — スライド作成

HTML 1 枚 (Artifact で公開)。作成前に artifact-design skill を読む。

- 1 論点 = 1 スライド。構成の基本: ①今回の全体像 → ②〜⑧各論点 (何を作った / なぜ / 動くもの・証拠) → ⑨PO 判断事項 → ⑩次の一手
- 各スライドに: 図解 or スクショ (文字の壁にしない) / ▶ 音声プレイヤー / スライド送り (ボタン + キーボード)
- 比較表・mermaid は debrief と同じ流儀で

### Step 3 — ナレーション原稿

スライドごとに 30〜60 秒相当。**書き言葉ではなく話し言葉**で書く (「〜です。ここでのポイントは〜」)。専門用語は初出時に一言添える。原稿はスライドの `<details>` にも収録 (文字でも追える保険)。

### Step 4 — 音声合成 (VOICEVOX)

1. `cicd/scripts/local-voicevox/start-voicevox.sh` でローカル engine を起動 (docker。daemon が落ちていれば `dockerd` を起動する。**イメージ pull のディスク残量とネットワークポリシーに注意** — 取得できない場合は Step 5 のフォールバックへ)
2. スライドごとに `/audio_query` → `/synthesis` で WAV 生成。**`speedScale` は 1.5 を既定にする** (briefing #1 で PO が「1.5 倍が聞きやすい」と評価)
3. 圧縮: ffmpeg があれば opus/mp3 化 (無ければ `apt-get install -y ffmpeg` を試す)。合計が Artifact の 16MB 制限に収まること。収まらなければ原稿を短くする (音質を落とすより先に)
4. data URI で `<audio>` に埋め込み。**埋め込み後は必ず JS の構文チェックと機能確認をする** — briefing #1 で、プレイヤー差し替えの正規表現置換がスライド送り関数 `show()` ごと巻き込んで削除し、ページングが壊れた実績あり (音声部分だけ見て公開しない)
5. **フォールバック**: engine が使えない環境では、ブラウザの speechSynthesis で原稿を読み上げる「▶ (ブラウザ読み上げ)」ボタンに切り替える。「音声なしで公開」はしない (聞き流し要件が PO 決定のため)

### Step 5 — 開催 (プレゼンター進行)

1. Artifact URL を渡し、「スライド 1 から。音声を再生しながら見てください」で開始
2. チャットでは 1 枚ごとに「▶ スライド N: {要点 1〜2 行}」だけ書き、**まとめて全部説明しない** (PO のペースで進む)
3. PO の質問には真実ソース (コード / ADR / PR) をその場で引いて答え、答えたら「スライド N に戻ります」で復帰
4. 承認事項 (rubric / Proposed ADR / Go・NoGo) は該当スライドの直後に **AskUserQuestion (選択肢形式)** で取る (ADR 0020)
5. 曖昧そうな反応があった論点は角度を変えて言い直す (debrief の逆質問と同じ目的。ただし報告会ではクイズ形式を強制しない)

### Step 6 — 記録

`docs/debrief/journal.md` の先頭にエントリ追記 (`## YYYY-MM-DD — briefing (#N, テーマ)`): 対象 / 決定 (承認事項の結果) / 質疑で曖昧だった箇所 / 持ち越し。音声つき資料の再生成に使った原稿・スクリプトは scratchpad 扱いで commit しない (資料はエフェメラル、記録は journal と GitHub)。

## やらないこと

- ❌ 動画化 (割り込めなくなる)
- ❌ 「資料を読んでおいてください」で終える
- ❌ 進捗数字の集計 (それは `/status`)、新設計の起案 (それは design-gate)、理解確認クイズの強制 (それは debrief)
- ❌ スライド内容のハードコード (毎回ライブ生成)

## 失敗時の挙動

- VOICEVOX が起動できない → speechSynthesis フォールバック (Step 4-5)。それも不可なら通常の debrief 形式に切り替えて PO に明示
- 16MB に収まらない → 原稿短縮 → それでも無理ならスライドを 2 部構成に分割
