# explain

user の「あれなんだっけ?」「これどういう仕組み?」「なんでこうしたんだっけ?」に、**真実ソースをその場で引いて、図解つきで即答する**。長い調査レポートではなく、まず 1 画面で全体像 → 聞かれたら深掘り、の順。

## いつ起動するか

- user がリポジトリの設計・構成・過去の判断・使っている技術について質問したとき (「〜ってどうなってたっけ」「〜の流れ見せて」「なんで〜?」)
- `/explain {トピック}` で明示呼び出しされたとき
- **起動しない場合**: 進捗の質問 (→ `/status`)、新しい設計の相談 (→ design-gate の前段として通常対話)

## 設計思想

- **真実ソースから毎回生成**。判断 = `docs/adr/`、UI = `docs/frontend/ui_specs/`、API = `docs/api/*.yaml`、手順 = `docs/runbooks/`、挙動 = コードそのもの。skill や記憶の中のスナップショットで答えない。ソースと実装が乖離していたら乖離ごと報告する
- **図が先、文章は従**。構成・フロー・関係は mermaid 図 1 枚から入る。文章は図の補足
- **1 画面で答える**。まず全体像を 1 レスポンスに収め、深掘りは user の追撃を待つ
- **出典を必ず付ける**。「どの doc / どのファイルにそう書いてあるか」をリンクで示し、user が自分で辿れるようにする

---

## 手順

### Step 1 — 質問の型と真実ソースを特定

| 質問の型 | 引く場所 |
| --- | --- |
| なぜ〜にした? (判断) | `docs/adr/` を grep → 該当 ADR |
| 〜の仕組み・流れは? (構成) | `CLAUDE.md` Architecture / `docs/design/` / コード |
| 画面・UI は? | `docs/frontend/ui_specs/*.mdx` / `mockApi.ts` |
| API の形は? | `docs/api/*.yaml` / zod・pydantic 定義 |
| 手順は? (deploy 等) | `docs/runbooks/` |
| 一般技術 (tRPC とは等) | 一般知識 + **このリポジトリでの使われ方** (コードを引く) |

複数に跨る質問は跨ったまま答える (無理に 1 ソースに丸めない)。

### Step 2 — 可視化して答える

チャット内で完結させるのが既定 (即答性が価値)。構成は:

1. **mermaid 図 1 枚** — 質問に合わせた形 (flowchart = 流れ / graph = 関係 / sequenceDiagram = やり取り / 比較なら表)
2. **要点 3〜5 行** — 図の読み方と結論
3. **出典リンク** — `docs/adr/NNNN-*.md` や `path/to/file.ts:行` の形で

図が複数要る・インタラクティブに見たい・user が「レポートで」と言った場合のみ、HTML 1 枚 (Artifact ツールが使える環境ではそれで公開。無ければ HTML ファイルを書いて渡す) に格上げする。

### Step 3 — 深掘りに応じる

user の追撃 (「もっと詳しく」「この部分は?」) にはコード・docs を開いて答える。会話が「この設計を変えたい」に発展したら、explain の範囲を出て通常の設計対話 → design-gate の流れに引き継ぐ。

## やらないこと

- ❌ 記憶・スナップショットからの回答 (毎回ソースを引く。引けなければ「どこにも書かれていない」と答える)
- ❌ 聞かれていない範囲への拡張 (1 画面で答え、深掘りは待つ)
- ❌ 設計の変更・ADR の起案 (それは design-gate / 通常対話。ここは読み取り専用)
- ❌ 進捗集計 (それは `/status`)

## 失敗時の挙動

- 真実ソースに記述が無い → 「docs に無い」と明示した上で、コードから読み取れる事実だけを答え、doc 化 (ADR / MDX) の要否を 1 行で提案
- ソースと実装が乖離 → 乖離を隠さず両方見せる (どちらが真実とされているかは `docs/documentation/strategy.md` の分担に従う)
