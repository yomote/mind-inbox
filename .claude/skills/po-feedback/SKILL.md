# po-feedback

user のプロダクトオーナーとしての動き方を、**実際に起きたことを証拠として**フィードバックする。お世辞は書かない (user が明示的に辛口を要求して作られた skill)。ただし辛口 = 攻撃ではない — 指摘には必ず「次にどうするか」を付ける。

## いつ起動するか

- user が `/po-feedback`、「指示の出しっぷりどう?」「進め方に文句ある?」等と言ったとき
- `debrief` skill の締めに 1 コーナーとして (毎回 2〜3 分ぶん。これが「定期的」の実装)

## 設計思想

- **証拠ベースのみ**。一般論の PM 論・教科書的アドバイスは書かない。このリポジトリのセッション記録・成果物から観測できた事実だけを根拠にする
- **エージェント側の視点を正直に**。「この指示はこう曖昧で、私はこう解釈で補った。外れていたらこのコストだった」— 人間の部下は言いにくいことを、この skill は言う
- **良い点も証拠つきで**。褒めるときも「なぜそれが効いたか」を構造で説明する (temperament としての褒めではなく再現可能にする)
- **1 回 1 アクション**。指摘を並べて終わらず、「次の期間で 1 つだけ変えるなら」に絞って提案する

## 手順

### Step 1 — 証拠を集める

前回の po-feedback (journal に記録) 以降を対象期間として:

- `docs/debrief/journal.md` — 意思決定の記録と持ち越し
- `docs/adr/` — Proposed のまま滞留している ADR の数と経過日数
- 直近の Issue / PR — スコープ宣言の有無、user コメントの具体性、放置されている確認事項
- **このセッション (起動されたセッション) の会話履歴** — user の指示と、エージェントが解釈で補った箇所

### Step 2 — 観点別に評価する

| 観点 | 見るもの | 悪いサイン |
| --- | --- | --- |
| **曖昧さ→解釈コスト** | エージェントが「〜と解釈しました」と補った回数・重大度。解釈確認に user が答えたか | 解釈表明が未確認のまま実装に進んだ箇所 |
| **スコープ宣言** | 「今回やること/やらないこと」を user が言語化したか (Issue / マイルストーン / 会話) | 受け入れ基準がエージェントの推測任せ (release-gate の R0 が機能しない) |
| **意思決定の滞留** | Proposed ADR の滞留、人間側 1 クリック作業 (設定・承認) の放置、返答待ちの質問 | 仕組みを作ったのに人間側の宿題で強制力が未完成 |
| **方向修正の質** | フィードバックが早期か・具体か・理由つきか | 完成後のちゃぶ台返し / 「なんか違う」だけで根拠なし |
| **仕組み化の判断** | 反復作業を skill/Routine に落とす判断、コスト感覚 | 同じ手作業の放置、逆に使わない仕組みの量産 |

### Step 3 — 出力

```markdown
## PO フィードバック ({期間})

**総評 1 行** (辛口 OK)

### 👍 効いていたこと (証拠つき、最大 3)
- {観測事実} → {なぜ構造的に良いか}

### 👎 コストになっていたこと (証拠つき、最大 3)
- {観測事実} → {実際に発生した/しかけたコスト} → {次にどうするか}

### 📌 次の期間で 1 つだけ変えるなら
{1 アクション。測定可能な形で}
```

### Step 4 — journal に記録

`docs/debrief/journal.md` に `po-feedback` エントリを追記する (次回の起点マーカー + 前回の「1 つだけ」が実行されたかの追跡用)。

## やらないこと

- ❌ 一般論の PM 教科書アドバイス (証拠が引けない指摘はしない)
- ❌ お世辞・励まし目的の水増し (それは skill の存在意義に反する)
- ❌ エージェント側の失敗を user のせいにする (解釈ミスの責任配分は正直に書く)
- ❌ 3 つ以上の「変えること」の同時提案 (1 つに絞る)

## 失敗時の挙動

- 前回起点が journal に無い (初回) → 直近 2 週間 or 直近の大きな作業単位を対象にする
- 証拠が少なすぎる (会話が短い等) → 「今回は材料不足」と正直に言い、無理に指摘を作らない
