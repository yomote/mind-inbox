# design-gate

「設計して、開発始めましょう」の**前に**挟む同期ゲート。設計を user に分かる形で可視化し、理解確認の対話をして、**user の承認が出てから**実装に入る。目的は検問ではなく、(1) 欲しいものと違うものを作り始める前に止めること、(2) user がアーキテクチャを自分の言葉で理解した状態で開発が進むこと。

## いつ起動するか

- 新しい設計 (ADR 級判断 / v1 Phase 着手 / 新機能・新サービス) の**実装を始めようとする直前** — エージェント側から自発的に起動する。user の依頼を待たない
- user が `/design-gate` や「実装前に設計を説明して」等と明示したとき
- **起動しない場合**: バグ修正・typo・既承認設計の範囲内の作業 (ゲート済みの設計に従うだけの実装)。無人セッション (Routine 等) では起動できないので ADR 0014 の規律に従う (one-way door は実装せず Issue に質問を積む / two-way door は Proposed ADR で進めて debrief で追認)

## 設計思想

- **可視化ファースト**。文章の壁ではなく、図 (構成図 / データフロー / 選択肢比較表) を先に見せる。解説はライブの設計 docs・コードから毎回生成する (skill に内容を持たない)
- **理解確認は「穴の発見」のため**。クイズの正解率を競うのではなく、user の理解が曖昧な箇所を見つけて、そこを解説し直すために問う
- **承認は明示的に取る**。「反対が無ければ進める」ではなく、user が「この設計で進めてよい」と言うまで実装に入らない
- **user の懸念は設計に反映してから進む**。ゲートは一方通行のプレゼンではなく、設計を直す最後の安価なタイミング

## 手順

### Step 1 — 対象設計の真実ソースを集める

対象となる設計の根拠を読む: 該当する `docs/adr/`・`docs/design/`・`docs/frontend/ui_specs/`・関連 Issue。この設計に対応する ADR がまだ無ければ、**先に ADR を `Status: Proposed` で書く** (CLAUDE.md のルールどおり)。

### Step 2 — 可視化して提示する

以下を user に見せる。小さい設計ならチャット内 (mermaid 図 + 表)、大きい設計なら HTML レポート 1 枚 (Artifact ツールが使える環境ではそれで公開。使えなければ HTML ファイルを書いて渡す):

1. **何を作るか** — 1〜3 文 + 画面/API の具体例
2. **構成図** — 登場するコンポーネントとデータの流れ (mermaid)
3. **到達経路を全部数える** — 図に矢印を 1 本描いたら、**「守るべき資源に、他に届くものは無いか」を必ず問う** ([ADR 0017](../../../docs/adr/0017-runtime-verification-in-the-loop.md))。守るべき資源 (課金するもの / データ / 外部への書き込み) を起点に、到達しうる経路を列挙して図に載せる。**意図した経路だけを描くと、2 本目の扉に気づかない** — epic #70 で、認可の門を Functions に置いたのに、OpenAI の鍵を実際に握る ai-agent が無認可で公開されたままだった実例がある (#86)
4. **主要な判断と理由** — 「なぜ X で Y でないか」を判断ごとに 1 行 + 捨てた代替案
5. **user への影響** — できるようになること / 制約として受け入れること / 変更コスト (これは後から変えやすい・変えにくい)
6. **どう動作検証するか** — 実装後に**何を叩けば「効いている」と言えるか**を先に決める ([ADR 0017](../../../docs/adr/0017-runtime-verification-in-the-loop.md))。「設定したか」ではなく**振る舞い**で書く (例: 「EasyAuth を有効にする」ではなく「未認証で叩いて 401 が返る」)。ブラウザが要る場合は、ローカル (mock + 認証なし) で見られる範囲と、**人の目が必要な範囲**を分けて示す

### Step 3 — 理解確認の対話

`AskUserQuestion` (使える環境なら) または通常の対話で、**2〜3 問**の理解確認をする。問いは「この設計だと、〜のとき何が起きる?」「なぜ Z を使わなかったと思う?」のような、設計の帰結・トレードオフを問う形にする (用語の暗記を問わない)。

- 答えが合っていたら次へ。曖昧・誤解があったら**その箇所を別の角度で解説し直す** (責めない。図を変える・具体例を出す)
- user からの質問には、必要ならコードや docs を開いて答える

### Step 4 — 懸念の反映と承認

- user の懸念・修正要望が出たら設計 (ADR / design doc) に反映し、影響があれば Step 2 の可視化を更新して再提示
- 最後に承認を明示的に取る: **「この設計で実装に進めてよいか」**。選択肢は 承認 / 修正して再提示 / 保留 (実装に入らない)
- 承認されたら、対象 ADR の Status を `Proposed` → `Accepted` に更新する (user の承認がここで入った記録になる)

### Step 5 — 記録

`docs/debrief/journal.md` の先頭にエントリを追記 (形式は journal 冒頭参照): 日付 / design-gate / 対象設計 / user の決定 (承認・修正点) / 理解確認で見つかった学びメモ。ADR の Status 変更とあわせてコミットする。

## やらないこと

- ❌ 承認前の実装着手 (ゲートの意味が無くなる)
- ❌ 設計内容の skill 内ハードコード (毎回ライブの docs / コードから生成)
- ❌ 形式的なクイズの出しっぱなし (答えの正誤より、曖昧な箇所の再解説が本体)
- ❌ user の懸念を「後で直す」で流すこと (ゲートは設計を直す最後の安価なタイミング)

## 失敗時の挙動

- user が応答できない (無人セッション) → ゲートは開催しない。ADR 0014 の規律に従う
- 対象設計の docs が存在しない → まず ADR / design doc を Proposed で書くところから始める
- `AskUserQuestion` が使えない → 通常のチャット対話で同じ内容を聞く
